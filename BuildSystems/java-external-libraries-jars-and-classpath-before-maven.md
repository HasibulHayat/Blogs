# Java External Libraries, JAR Files, and Classpaths

## 1. What We Are Learning

Before using Maven or Gradle, it is useful to understand how Java handles:

- Source code and compiled class files
- External libraries
- JAR files
- Compile-time and runtime classpaths
- Missing-class errors
- Separating source files from compiled output

We will use Jackson, a Java library that converts Java objects to JSON.

## 2. Project Structure

We created a project with separate folders for source code, libraries, and compiled output:

```text
JavaLibraryTest/
├── src/
│   └── Main.java
├── lib/
│   ├── jackson-databind.jar
│   ├── jackson-core.jar
│   └── jackson-annotations.jar
└── out/
    ├── Main.class
    └── Main$Person.class
```

| Folder | Purpose |
|---|---|
| `src/` | Java source files that developers write |
| `lib/` | External library JAR files |
| `out/` | Compiled `.class` files generated by the Java compiler |

Keeping these separate makes a project easier to understand and maintain.

## 3. What Is a JAR File?

A **JAR** (Java Archive) is a package file that can contain compiled Java classes and other resources. A JAR is commonly used to distribute a Java library.

Our program uses Jackson's `ObjectMapper` class:

```java
import com.fasterxml.jackson.databind.ObjectMapper;
```

We did not write `ObjectMapper`; it is provided by Jackson, an external library.

For this example, we downloaded three JARs:

- **`jackson-databind.jar`** — provides `ObjectMapper` and object-to-JSON data binding.
- **`jackson-core.jar`** — provides core JSON processing functionality.
- **`jackson-annotations.jar`** — provides annotation types used by Jackson.

Databind depends on the other two Jackson components. This illustrates that one library can depend on other libraries. These are called **dependencies**.

## 4. The Java Program

Our `src/Main.java` file contains:

```java
import com.fasterxml.jackson.databind.ObjectMapper;

public class Main {

    public static void main(String[] args) throws Exception {
        Person person = new Person("Alex", 25);

        ObjectMapper mapper = new ObjectMapper();

        String json = mapper.writeValueAsString(person);

        System.out.println(json);
    }

    public static class Person {
        public String name;
        public int age;

        public Person(String name, int age) {
            this.name = name;
            this.age = age;
        }
    }
}
```

The program creates a `Person` object, asks Jackson to convert it to JSON, and prints the result:

```json
{"name":"Alex","age":25}
```

The `Person` class is nested inside `Main`. Java produces a separate class file for each class.

## 5. Compile the Program

From the `JavaLibraryTest` project directory, we ran:

```bash
javac -cp "lib/*" -d out src/Main.java
```

Let's break down the command.

### `javac`

The Java compiler. It converts Java source code into JVM bytecode stored in `.class` files.

### `-cp "lib/*"`

`-cp` means **classpath**. The classpath tells Java tools where to look for classes.

Here, `lib/*` means to include the JAR files inside the `lib/` directory. The compiler needs to find Jackson's classes to resolve the import and compile the program.

The quotes keep the wildcard expression together as one shell argument. Java understands the JAR wildcard in this classpath form.

### `-d out`

`-d` specifies the destination directory for compiled class files. In this case, generated class files go into `out/`.

### `src/Main.java`

The source file to compile.

After compilation, we ran:

```bash
find out -type f
```

The result was:

```text
out/Main$Person.class
out/Main.class
```

Why two class files?

- `Main.class` contains the compiled `Main` class.
- `Main$Person.class` contains the compiled nested `Person` class.

A Java source file can define multiple classes, and the compiler can generate a separate `.class` file for each one.

## 6. Compile-Time Classpath vs. Runtime Classpath

A critical idea is that **compiling a program and running it are separate operations**.

### Compile-time classpath

This command makes Jackson available to the compiler:

```bash
javac -cp "lib/*" -d out src/Main.java
```

The compiler needs Jackson to understand the `ObjectMapper` reference and check that the code is valid.

### Runtime classpath

After compilation, we ran:

```bash
java -cp "out:lib/*" Main
```

The JVM needs to find both:

- `out/` — our compiled application classes
- `lib/*` — the external Jackson classes

On Linux, a colon (`:`) separates entries in the classpath.

So `java -cp "out:lib/*" Main` means: look in `out/` and in the JAR files inside `lib/`, then run the `Main` class.

The output is:

```json
{"name":"Alex","age":25}
```

**Remember:** the compiler's classpath and the runtime classpath serve different stages. A library being available during compilation does not automatically make it available when the program runs.

## 7. Experiment: Remove the Library from the Runtime Classpath

We deliberately ran:

```bash
java -cp "out" Main
```

This tells Java to search only in `out/`. It does not include the Jackson JARs in `lib/`.

We received an error similar to:

```text
Exception in thread "main" java.lang.NoClassDefFoundError:
    com/fasterxml/jackson/databind/ObjectMapper
    at Main.main(Main.java:8)
Caused by: java.lang.ClassNotFoundException:
    com.fasterxml.jackson.databind.ObjectMapper
```

### Why did this happen?

1. The JVM found `Main.class` in `out/`.
2. It started executing the program.
3. The program reached `new ObjectMapper()`.
4. The JVM needed Jackson's `ObjectMapper` class.
5. Jackson was not on the runtime classpath, so the JVM could not load it.

The source code and compiled `Main.class` file still existed. The problem was that a required dependency was missing from the runtime classpath.

### `ClassNotFoundException` and `NoClassDefFoundError`

These related errors are not identical:

- **`ClassNotFoundException`** is thrown when a class-loading operation explicitly attempts to load a class and cannot find it.
- **`NoClassDefFoundError`** occurs when running code requires a class definition that the JVM cannot load.

In our output, `ClassNotFoundException` appeared as the cause of `NoClassDefFoundError`.

For now, remember the practical lesson: a missing dependency can stop a program from running even if your own code compiled successfully.

### Restore the working command

Run:

```bash
java -cp "out:lib/*" Main
```

Expected output:

```json
{"name":"Alex","age":25}
```

## 8. Why Do We Need Build Tools?

Imagine a larger application that depends on Spring Web, Spring Security, Spring Data JPA, a PostgreSQL JDBC driver, Jackson, logging libraries, and many other components.

Without a build tool, you would need to manage the JAR files and classpaths yourself. You would have to:

1. Find and download the correct JAR for every library.
2. Identify each library's dependencies.
3. Download those dependencies too.
4. Avoid incompatible versions.
5. Provide the correct classpath when compiling.
6. Provide the correct classpath again when running.
7. Repeat the setup on another developer's computer or a deployment server.

This becomes tedious and error-prone as a project grows.

Build tools such as Maven and Gradle help automate dependency resolution and the build process. They can download declared dependencies, resolve transitive dependencies, compile source code, run tests, and package the application.

A **transitive dependency** is a dependency required by a library that your project uses. For example, your project directly uses Jackson Databind, which in turn requires other Jackson components.

Build tools do not make dependencies part of Java itself. They manage the libraries and coordinate the build. How an application is packaged determines how its dependencies are made available at deployment and runtime.

We will learn Maven and Gradle separately later. For now, the important thing is to understand the manual process they help automate.

## 9. Commands to Remember

| Command | Meaning |
|---|---|
| `javac -cp "lib/*" -d out src/Main.java` | Compile source code using JARs in `lib/`, putting class files in `out/` |
| `find out -type f` | List files under `out/` |
| `java -cp "out:lib/*" Main` | Run `Main` with application classes and external JARs available |
| `java -cp "out" Main` | Run with only `out/` on the classpath; Jackson will be missing in this example |

## 10. Key Takeaways

- `.java` files contain source code; `.class` files contain compiled JVM bytecode.
- A JAR packages compiled classes and resources, and is commonly used to distribute a library.
- An external library provides code that your application uses.
- A library can depend on other libraries.
- The **compile-time classpath** helps the compiler locate classes needed to compile your code.
- The **runtime classpath** helps the JVM locate classes needed while the program runs.
- `-d out` keeps compiled class files separate from source files.
- On Linux, `:` separates classpath entries.
- `NoClassDefFoundError` can occur when a class required at runtime cannot be loaded.
- Manual dependency management becomes difficult as projects grow. Maven and Gradle automate much of this work.
