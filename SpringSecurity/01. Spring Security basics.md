# Understanding Spring Security from the Core

A beginner-friendly guide to understanding **why Spring Security exists,
how it works, and how it protects a Spring Boot application**.

<br>
<br>

## 1. Authentication vs Authorization

```

  Authentication                      Authorization
  -------------------------------     -----------------------------------

  Who are you?                        What can you do?

  Verifies identity                   Checks access rights

  Usually happens during login or     Happens when accessing protected
  token validation                    resources

  Example: Is this username/password  Example: Can this user approve this
  correct?                            payment?

```

Remember:

**Authentication identifies the user. Authorization controls the user's
access.**

You need both.

<br>

## 2. What happens after a user logs in?

Let's say Hasib successfully logs in.

Your backend now knows that the user is Hasib.

But your application needs to recognize that identity when Hasib makes
another request.

For example:

``` http
GET /api/apartments
```

How does the backend know who sent this request?

HTTP is fundamentally a request-and-response protocol. Your application
should not assume that it automatically remembers the identity of a user
from an earlier request.

You need a way to establish the user's identity on subsequent requests.

There are different approaches.

## Approach 1: Session-based authentication

In traditional session-based authentication:

1.  The user logs in.
2.  The server verifies the credentials.
3.  The server creates a session.
4.  The browser receives a session identifier, commonly through a
    cookie.
5.  The browser sends that cookie with subsequent requests.
6.  The server uses the session identifier to find the session and its
    authenticated user.

Conceptually:

``` text
LOGIN
  |
  v
Server verifies credentials
  |
  v
Server creates a session
  |
  v
Browser receives session cookie
  |
  v
Browser sends cookie with next request
  |
  v
Server identifies the user
```

The server maintains session state.

## Approach 2: Token-based authentication

Another approach is token-based authentication.

This is the approach we are using for our API with JWT access tokens.

JWT stands for JSON Web Token.

A simplified flow:

1.  The user logs in.
2.  The backend verifies the credentials.
3.  The backend generates an access token.
4.  The frontend receives the token.
5.  The frontend sends it with subsequent requests.
6.  The backend validates the token and establishes the user's identity
    for that request.

For example:

``` http
GET /api/apartments
Authorization: Bearer <access-token>
```

The token is a signed piece of information that the backend can
validate.

### Why do we need to send the token repeatedly?

Because each request needs to establish its own authentication context.

For example:

``` text
Request 1: GET /api/apartments
Request 2: GET /api/payments
Request 3: POST /api/payments
```

The backend must authenticate each request.

In a stateless token-based API, the access token is normally sent with
every protected request.

### Session vs token
```

  -----------------------------------------------------------------------
  Session-based                       Token-based
  ----------------------------------- -----------------------------------
  
  Server maintains session state      Token carries signed claims

  Browser commonly sends a session    Client commonly sends a Bearer
  cookie                              token

  Server looks up the session         Server validates the token

  Authentication state is stored      Authentication can be established
  server-side                         from the token

```

Neither approach is automatically more secure in every situation.
Security depends on how each is implemented.

## 3. What is a request, and where does security happen?

Before understanding Spring Security, we need to understand the journey
of an HTTP request.

Suppose the frontend sends:

``` http
GET /api/apartments
```

Your Spring Boot application runs inside a servlet container such as
Tomcat.

A simplified request journey is:

``` text
HTTP Request
     |
     v
Tomcat (Servlet Container)
     |
     v
Servlet Filters
     |
     v
Spring MVC
     |
     v
Controller
     |
     v
Service
     |
     v
Repository
     |
     v
Database
```

Let's understand these parts.

### 3.1 Tomcat --- receiving the request

Tomcat is a servlet container.

It receives incoming HTTP requests and manages the servlet
infrastructure that processes them.

Think of Tomcat as the entrance to your backend application.

### 3.2 Servlet Filters --- processing requests before controllers

Before a request reaches Spring MVC, it can pass through servlet
filters.

A filter can inspect or process a request.

For example:

-   Log the incoming request.
-   Check request headers.
-   Apply CORS handling.
-   Perform authentication-related work.
-   Reject a request.

A filter can also allow the request to continue.

Think of filters as checkpoints before the request reaches the
application endpoint.

### 3.3 Spring MVC --- routing the request

Once the request passes through the filter infrastructure, it reaches
Spring MVC.

Spring MVC determines which controller should handle the request.

For example:

``` java
@GetMapping("/apartments")
public List<ApartmentDto> getApartments() {
    return apartmentService.getAllApartments();
}
```

Spring MVC routes the request to the appropriate controller method.

### 3.4 Controller, Service and Repository

These are the application layers that perform the requested business
operation.

-   Controller receives and responds to the HTTP request.
-   Service handles business logic.
-   Repository communicates with the database.

The important thing to remember:

**Security filters normally process the request before Spring MVC routes
it to your controller.**

<br>

## 4. What is Spring Security?

Now we can answer the main question.

Spring Security is a framework that helps protect Java and Spring
applications.

It provides functionality for:

-   Authentication
-   Authorization
-   Password handling
-   Security-related request processing
-   Protection against common web attacks
-   Security error handling

But how does it actually work?

A central part of Spring Security is its use of filters.

### 4.1 Spring Security is built around filters

Remember that servlet filters can intercept requests before they reach
Spring MVC.

Spring Security uses this same mechanism.

It organizes security-related filters into a security filter chain.

Each filter has a responsibility.

For example, different filters can participate in:

-   Preparing the security context
-   Processing authentication
-   Handling authentication-related exceptions
-   Checking authorization

You do not need to write all these filters yourself. Spring Security
provides many built-in filters.

You configure the security behavior, and Spring Security uses the
appropriate filters to enforce it.

### 4.2 A simplified picture

``` text
Incoming HTTP Request
         |
         v
Tomcat
         |
         v
Servlet Filter Infrastructure
         |
         v
Spring Security
         |
         +--> Establish authentication
         |
         +--> Handle security exceptions
         |
         +--> Check authorization
         |
         v
Spring MVC
         |
         v
Controller
```

This is a conceptual picture. Spring Security's actual filter chain
contains more steps, and their exact order depends on the configuration.

### What if a request fails security checks?

Suppose a user tries to access an administrator-only endpoint without
the required authority.

Spring Security can reject the request before it reaches the controller.

That is one of its most important benefits.

You do not have to write authentication checks inside every controller
method.

# Part 7 --- What happens when someone accesses a protected endpoint?

Let's walk through a complete example.

Imagine an apartment owner wants to view their apartment.

The frontend sends:

``` http
GET /api/apartments/123
Authorization: Bearer <access-token>
```

Here is the simplified flow:

``` text
1. Frontend sends request
          |
          v
2. Tomcat receives request
          |
          v
3. Servlet filter infrastructure processes it
          |
          v
4. Spring Security processes the request
          |
          v
5. Access token is validated
          |
          v
6. User's identity is established
          |
          v
7. Authorization rules are checked
          |
          v
8. Request reaches Spring MVC
          |
          v
9. Controller receives request
          |
          v
10. Service checks apartment-level access
          |
          v
11. Repository retrieves permitted data
          |
          v
12. Response returns to frontend
```

Notice that there are two important security decisions.

**First:** Is the user authenticated?

**Second:** Is the user allowed to access the requested resource?

These are separate checks.

# Part 8 --- Roles and Permissions

Now let's understand how an application decides what users are allowed
to do.

Two common concepts are roles and permissions.

## 8.1 What is a role?

A role represents a category of user.

For example:

``` text
ADMIN
STAFF
STANDARD_USER
```

A role usually represents a collection of responsibilities.

For example, an administrator might be allowed to:

-   Manage apartments
-   Manage users
-   Manage residents
-   View financial reports

## 8.2 What is a permission?

A permission represents a specific capability.

For example:

``` text
apartment:read
apartment:create
apartment:update
apartment:delete

payment:read
payment:create
payment:approve
```

Instead of checking whether someone is an administrator everywhere, your
application can check whether they have the particular permission
required for an action.

## 8.3 How do roles and permissions relate?

Imagine this relationship:

``` text
ADMIN
  |
  +--> apartment:read
  +--> apartment:create
  +--> apartment:update
  +--> apartment:delete
  +--> payment:read
  +--> payment:approve


STAFF
  |
  +--> apartment:read
  +--> payment:read


STANDARD_USER
  |
  +--> apartment:read
```

A role can be associated with multiple permissions.

A user is assigned a role, and that role determines the user's granted
capabilities.

This is a common approach called Role-Based Access Control (RBAC).

The exact design depends on your application.

# Part 9 --- An important security concept: object-level access

There is something else you must understand, especially for an
apartment-management application.

Suppose an apartment owner has the permission:

``` text
apartment:read
```

Does that mean they can view every apartment?

Absolutely not.

Imagine:

``` text
Apartment 101
    Owner: Hasib

Apartment 102
    Owner: Rahim

Apartment 103
    Owner: Karim
```

Hasib should only be able to access Apartment 101 if that is the only
apartment he is entitled to access.

Even if he has the general permission to read apartments, he should not
be able to access Apartment 102 by changing the URL:

``` http
GET /api/apartments/102
```

Your backend must check whether Hasib is actually associated with
Apartment 102 in a way that grants access.

This is called **object-level authorization**.

There are two different questions:

1.  Does the user have permission to read apartment information?
2.  Is the user allowed to read this particular apartment?

You need both.

Never rely on frontend restrictions to enforce this. The backend must
perform the check.

# Part 10 --- Multi-tenant security

Our application is designed for multiple tenants.

This introduces another important security boundary.

Imagine:

``` text
Tenant A
  |
  +--> Admin A
  +--> Apartment A1
  +--> Apartment A2


Tenant B
  |
  +--> Admin B
  +--> Apartment B1
  +--> Apartment B2
```

Admin A must never be able to access Tenant B's apartments.

Even if Admin A has the permission:

``` text
apartment:read
```

that permission must not grant access to apartments belonging to another
tenant.

Your backend needs to enforce tenant isolation.

For example, a database query should conceptually look like:

``` sql
SELECT *
FROM apartment
WHERE id = :apartmentId
  AND tenant_id = :currentTenantId;
```

The current tenant identity must come from trusted authentication
context, not from a tenant ID that the frontend can freely change.

So, in a multi-tenant application, you need to think about three levels:

1.  **Authentication:** Who is the user?
2.  **Permission authorization:** What actions can the user perform?
3.  **Resource and tenant authorization:** Which particular records can
    the user access?

These work together.

# Part 11 --- What happens when access is denied?

There are two important HTTP status codes to understand.

## 401 --- Unauthorized

This normally means that the request has not been successfully
authenticated.

Examples:

-   The user did not provide an access token.
-   The token is invalid.
-   The token has expired.

In simple terms:

> We cannot establish who you are.

## 403 --- Forbidden

This normally means that the user is authenticated but does not have
permission to perform the requested action.

For example:

-   A resident tries to access an administrator-only endpoint.
-   A user tries to perform an action for which they do not have the
    required permission.

In simple terms:

> We know who you are, but you are not allowed to do this.

Remember:

  Situation                                   Typical response
  ------------------------------------------- ------------------
  Missing or invalid authentication           401
  Authenticated but insufficient permission   403

# Part 12 --- What about security beyond authentication?

Spring Security is not only about logging in and checking permissions.

It also helps protect applications against other security problems.

Two important examples are:

## 12.1 CSRF

CSRF stands for Cross-Site Request Forgery.

Imagine a user is logged into a website using cookie-based
authentication.

An attacker tricks the user's browser into sending an unwanted request
to that website.

Because the browser automatically attaches certain cookies, the request
might be treated as authenticated.

CSRF protection helps defend against this kind of attack.

The important point:

If your authentication uses cookies, you need to think carefully about
CSRF protection.

Do not disable it without understanding how your browser sends
authentication credentials.

## 12.2 CORS

CORS stands for Cross-Origin Resource Sharing.

Imagine:

``` text
Frontend: https://app.example.com
Backend:  https://api.example.com
```

These are different origins.

Browsers enforce cross-origin restrictions. Your backend needs an
appropriate CORS policy to allow the intended frontend to communicate
with it.

CORS is not authentication.

It does not prove who a user is, and it does not prevent someone from
calling your API using tools outside the browser.

# Part 13 --- Putting everything together

Let's summarize the complete idea using one example.

Hasib wants to view his apartment.

### Step 1: Login

Hasib enters his username and password.

The backend verifies his credentials.

If successful, the backend issues an access token.

### Step 2: Send a request

The frontend sends:

``` http
GET /api/apartments/123
Authorization: Bearer <access-token>
```

### Step 3: Request enters Tomcat

Tomcat receives the HTTP request.

### Step 4: Filters process the request

The request passes through the servlet filter infrastructure.

Spring Security processes it through its security filter chain.

### Step 5: Authentication

The access token is validated.

The backend establishes Hasib's authenticated identity.

### Step 6: Authorization

Spring Security checks whether Hasib has the required permission.

For example:

``` text
apartment:read
```

### Step 7: Business-level access check

The application checks whether Apartment 123 belongs to Hasib's tenant
and whether Hasib is entitled to access it.

### Step 8: Controller

If all checks succeed, Spring MVC routes the request to the appropriate
controller.

### Step 9: Response

The backend returns the permitted apartment information.

The complete simplified flow:

``` text
                 LOGIN
                   |
                   v
          Verify credentials
                   |
                   v
            Issue JWT token
                   |
                   v
       Frontend sends API request
                   |
                   v
              Tomcat
                   |
                   v
          Servlet Filter Chain
                   |
                   v
            Spring Security
                   |
                   v
          Validate access token
                   |
                   v
        Establish user identity
                   |
                   v
       Check roles and permissions
                   |
                   v
               Spring MVC
                   |
                   v
              Controller
                   |
                   v
               Service
                   |
                   v
       Check tenant/resource access
                   |
                   v
              Repository
                   |
                   v
               Database
                   |
                   v
             API Response
```

# Part 14 --- What you should remember

You don't need to memorize Spring Security's internal classes right now.

Understand these fundamental ideas:

  -----------------------------------------------------------------------
  Concept                             Meaning
  ----------------------------------- -----------------------------------
  Security                            Protecting application resources
                                      and operations

  Authentication                      Verifying who a user is

  Authorization                       Determining what a user can do

  Session                             Server-maintained authentication
                                      state

  Token                               A piece of data used to establish
                                      identity, commonly a signed JWT

  Servlet Filter                      Intercepts and processes requests
                                      before Spring MVC

  Filter Chain                        An ordered sequence of filters

  Spring Security                     A framework that uses filters and
                                      other mechanisms to provide
                                      application security

  Role                                A category of user responsibilities

  Permission                          A specific capability

  Object-level authorization          Checking whether a user can access
                                      a particular record

  Tenant isolation                    Preventing access across tenant
                                      boundaries
  -----------------------------------------------------------------------

## The five questions to ask whenever you build a protected feature

For every new endpoint in your application, ask:

1.  **Identity:** Who is making this request?
2.  **Authentication:** Have we successfully verified that identity?
3.  **Permission:** Is this user allowed to perform this type of
    operation?
4.  **Ownership:** Is this user allowed to access this particular
    resource?
5.  **Tenant:** Does this resource belong to a tenant the user is
    allowed to access?

If you consistently ask these five questions, you will develop a much
stronger understanding of application security.

# Final note

The most important thing is to understand that Spring Security is not
magic.

It is a framework that provides a structured way to handle security
concerns in your application.

The underlying ideas are quite straightforward:

-   Identify the user.
-   Verify their identity.
-   Determine what they can do.
-   Check which resources they can access.
-   Reject requests that violate these rules.

**Understand these concepts first. Learn the framework's classes and
configuration afterward.**
