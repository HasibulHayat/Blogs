# Core Concepts --- Phase 2, Lesson 4: Atomicity

## Introduction

In the previous lessons, we learned about:

-   Shared data and shared mutable state
-   Race conditions
-   Critical sections

Now we'll study a concept that explains why a simple-looking operation
can fail when multiple threads execute it concurrently:

**Atomicity**

This lesson covers what atomicity means, why operations such as

and how the idea applies to the Turf booking system.

## 1. What Is Atomicity?

An operation is **atomic** when it happens as one indivisible operation
from the perspective of other threads.

In simpler words:

Other threads cannot observe or interfere with the operation halfway
through it.

An atomic operation behaves as though it happened all at once.

Imagine a bank transfer of 500 taka from Account A to Account B.

The intended operation is:

1.  Subtract 500 from Account A.
2.  Add 500 to Account B.

If the operation is treated as one atomic unit, the system must not
expose a partially completed transfer as though it were complete.

Atomicity is about whether an operation can be observed in a partially
completed state.

## 2. Why Does `count++` Look Atomic but Isn't?

Consider:

``` java
public class Counter {

    private int count = 0;

    public void increment() {
        count++;
    }
}
```

It looks like one operation:

``` java
count++;
```

But conceptually, it involves three steps:

1.  Read the current value of `count`.
2.  Add one to that value.
3.  Write the new value back to `count`.

You can think of it as:

``` java
int current = count;
int updated = current + 1;
count = updated;
```

This is a conceptual expansion to help us understand the operation. The
compiler and runtime are free to use different implementation details,
but the important point is that `count++` is a read-modify-write
operation, not an atomic increment.

### Example: Two threads incrementing the same counter

Suppose `count` starts at `10`.

    Step Thread A          Thread B
  ------ ----------------- -----------------
       1 Reads `10`        
       2                   Reads `10`
       3 Calculates `11`   
       4                   Calculates `11`
       5 Writes `11`       
       6                   Writes `11`

The final value is `11`.

But two increments should have produced `12`.

One update has been lost.

This is a **lost update** problem, caused by concurrent execution of a
non-atomic read-modify-write operation.

## 3. Atomicity and Indivisibility

Let's compare two operations.

### Non-atomic read-modify-write

``` java
count++;
```

A thread can be interrupted or another thread can run between the
conceptual read and write steps. The operations can interleave.

### Atomic increment

An atomic increment is performed as one indivisible operation from the
perspective of competing threads.

If two threads each atomically increment a value that starts at `10`,
the final value will be `12`.

The key distinction is not how short the source code looks.

**A one-line statement is not necessarily atomic, and a multi-step
operation can be made atomic through an appropriate mechanism.**

## 4. Atomicity Does Not Mean the Whole Method Is Atomic

Consider:

``` java
public void transfer(Account from, Account to, int amount) {

    from.withdraw(amount);

    to.deposit(amount);
}
```

Even if `withdraw()` and `deposit()` are each individually thread-safe,
the complete transfer may not be atomic.

For example:

1.  The money is withdrawn from the first account.
2.  The application fails before depositing it into the second account.

The transfer is only partially completed.

This shows why we must identify the **logical operation** whose
correctness matters.

Sometimes one statement needs atomicity. Sometimes several statements
must be treated as one unit.

For a real bank transfer, the database transaction should usually make
the debit and credit succeed or fail together. We will study transaction
boundaries and database atomicity later in Phase 6.

## 5. Atomicity vs. Thread Safety

These terms are related, but they do not mean the same thing.

  -----------------------------------------------------------------------
  Concept                             Meaning
  ----------------------------------- -----------------------------------
  Atomicity                           An operation is indivisible from
                                      the perspective of other threads

  Thread safety                       A component behaves correctly when
                                      accessed concurrently according to
                                      its contract
  -----------------------------------------------------------------------

Atomicity is one tool or property that can help build thread-safe code.

However, making one operation atomic does not automatically make an
entire class thread-safe.

For example:

``` java
public class Counter {

    private int count = 0;

    public void increment() {
        count++;
    }

    public int getCount() {
        return count;
    }
}
```

Even if we replace the increment with an atomic operation, we still need
to consider the complete behavior of the class, including how values are
read and how multiple operations relate to one another.

Thread safety is a broader property.

## 6. How Java Provides Atomic Operations

Java provides classes in `java.util.concurrent.atomic` for common atomic
operations.

One example is `AtomicInteger`.

``` java
import java.util.concurrent.atomic.AtomicInteger;

public class Counter {

    private final AtomicInteger count = new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet();
    }

    public int getCount() {
        return count.get();
    }
}
```

Here:

``` java
count.incrementAndGet();
```

performs an atomic increment.

If multiple threads call `increment()` concurrently, each increment is
applied without the lost-update problem shown earlier.

### Common atomic classes

  Class                  Purpose
  ---------------------- ---------------------------------------
  `AtomicInteger`        Atomic operations on an integer
  `AtomicLong`           Atomic operations on a long
  `AtomicBoolean`        Atomic operations on a boolean
  `AtomicReference<T>`   Atomic updates to an object reference

We'll study atomic variables and compare-and-set (CAS) in detail in
Phase 4, Lesson 40.

For now, remember that atomic classes provide ready-made atomic
operations for supported value types.

## 7. Why `volatile` Does Not Make `count++` Atomic

This is an important distinction that often appears in interviews.

Consider:

``` java
public class Counter {

    private volatile int count = 0;

    public void increment() {
        count++;
    }
}
```

Does `volatile` make `count++` atomic?

**No.**

`volatile` provides visibility and ordering guarantees for accesses to
that variable. It does not turn a compound read-modify-write operation
into one indivisible operation.

Two threads can still do this:

1.  Both read the same value.
2.  Both calculate the same next value.
3.  Both write that value.

The lost update is still possible.

We will study `volatile` properly in Phase 3, Lesson 29.

For now, remember:

-   `volatile` helps with visibility and ordering.
-   It does not provide mutual exclusion.
-   It does not make `count++` atomic.

## 8. Atomicity vs. Visibility

Atomicity and visibility solve different concurrency problems.

  -----------------------------------------------------------------------
  Concept                             Main question
  ----------------------------------- -----------------------------------
  Atomicity                           Can another thread interfere with
                                      or observe an operation halfway
                                      through?

  Visibility                          When one thread changes a value,
                                      when will another thread see that
                                      change?
  -----------------------------------------------------------------------

A program can have one problem without the other.

For example:

-   A thread may perform a non-atomic increment and lose an update.
-   A thread may update a value, but another thread may not promptly
    observe that update because there is no appropriate visibility
    guarantee.

We will study visibility and the Java Memory Model in the next lessons.

## 9. Atomicity in the Turf Project

Imagine a turf has one slot remaining.

Two customers attempt to book that slot at almost the same time.

A simplified service might look like this:

``` java
public void bookSlot(Long slotId) {

    Slot slot = slotRepository.findById(slotId)
            .orElseThrow();

    if (slot.getAvailableSlots() > 0) {
        slot.setAvailableSlots(
                slot.getAvailableSlots() - 1
        );

        slotRepository.save(slot);
    }
}
```

The logical operation is:

1.  Read the available slot count.
2.  Check that at least one slot is available.
3.  Decrease the available count.
4.  Save the booking-related change.

If two requests read the value `1` before either request updates it,
both may decide that a slot is available.

Both may proceed.

This is a check-then-update operation. Protecting only the decrement is
not enough; the check and update must be coordinated as one logical
operation.

### An important backend distinction

A Java atomic class does not automatically solve a database booking
race.

For example, `AtomicInteger` coordinates threads that share that
particular in-memory object inside one JVM. It does not coordinate:

-   Multiple Spring Boot application instances
-   Multiple servers
-   Other applications writing to the same database
-   Database transactions running concurrently

For a real Turf booking system, correctness must be enforced at the
appropriate persistence boundary using database mechanisms such as
transactions, constraints, and locking or conditional updates.

We will study these backend techniques in Phase 6.

## 10. Common Interview Questions

### Q1. What is atomicity in concurrent programming?

Atomicity means an operation is indivisible from the perspective of
other threads. It cannot be observed or interfered with halfway through
its execution.

### Q2. Is `count++` atomic in Java?

No. It is a read-modify-write operation. Conceptually, it reads the
value, increments it, and writes the result. Concurrent threads can
interleave these steps and lose updates.

### Q3. Does a one-line statement have to be atomic?

No. Source-code length does not determine atomicity. A one-line
statement can involve multiple operations.

### Q4. Does `volatile` make `count++` atomic?

No. `volatile` provides visibility and ordering guarantees, but it does
not make compound operations such as increment atomic.

### Q5. What is the difference between atomicity and thread safety?

Atomicity describes whether an operation is indivisible. Thread safety
describes whether a component behaves correctly under concurrent access.
Atomic operations can help implement thread-safe components, but they do
not guarantee that an entire class is thread-safe.

### Q6. How can Java perform an atomic integer increment?

Use an atomic class such as `AtomicInteger` and call `incrementAndGet()`
or `getAndIncrement()`.

### Q7. If two methods are individually thread-safe, is calling them one after another automatically atomic?

No. The combined sequence may still be interrupted or interleaved with
other operations. The complete logical operation may need its own
coordination or transaction.

### Q8. Does an `AtomicInteger` solve double booking in a multi-instance Spring Boot application?

No. It only coordinates access to that in-memory object within the JVM
where it exists. Multiple application instances require coordination at
a shared system boundary, typically the database.

## 11. Practical Exercise

Create a `Counter` class with:

-   An integer field `count`, initially `0`.
-   An `increment()` method that performs `count++`.
-   A `getCount()` method.

Then:

1.  Create two threads.
2.  Make each thread call `increment()` 100,000 times.
3.  Start both threads.
4.  Wait for both threads to finish.
5.  Print the final counter value.

The expected value is:

``` text
200000
```

Run the program several times and observe whether the result is always
correct.

Then answer these questions:

1.  Why can the final value be lower than `200000`?
2.  Which part of `count++` is involved in the problem?
3.  Why does adding `volatile` to `count` not solve the lost-update
    problem?
4.  What Java class could provide an atomic increment?

**For this exercise, first reproduce and understand the problem. Don't
jump straight to the solution.**

1.  Atomicity means an operation is indivisible from the perspective of

2.  `count++` is a read-modify-write operation, not an atomic increment.
3.  Concurrent execution of non-atomic operations can cause lost
    updates.
4.  A one-line statement is not necessarily atomic.
5.  A logical operation can involve multiple statements.
