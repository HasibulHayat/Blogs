# Core Concepts --- Phase 2, Lesson 3: Critical Sections

## Introduction

In the previous lessons, we learned about shared data and race
conditions.

Now we will study a concept that helps us understand how to protect
shared data:

**Critical Sections**

This lesson covers what a critical section is, why it matters, mutual
exclusion, the classical requirements of the critical-section problem,
Java synchronization previews, and how the concept applies to a Spring
Boot booking system.

------------------------------------------------------------------------

## 1. What is a Critical Section?

A **critical section** is a section of code that accesses shared mutable
data or shared resources and therefore requires coordinated access to
prevent incorrect concurrent behavior.

In simpler words:

When multiple threads can access the same data, certain operations must
be protected so that they don't interfere with each other.

Consider:

``` java
public class Counter {

    private int count = 0;

    public void increment() {
        count++;
    }
}
```

Here:

``` java
count++;
```

is a critical section because:

-   `count` is shared between threads.
-   Multiple threads can execute `increment()` simultaneously.
-   `count++` is not atomic.
-   Concurrent execution can cause lost updates.

The critical section is the code that needs protection, not necessarily
the entire method or class.

## 2. Why Do We Need Critical Sections?

Let's revisit the counter example.

Suppose two threads increment the same counter, and `count` starts at
`10`.

Without coordination, this can happen:

    Step Thread A        Thread B
  ------ --------------- ---------------
       1 Reads 10        
       2                 Reads 10
       3 Calculates 11   
       4                 Calculates 11
       5 Writes 11       
       6                 Writes 11

The expected result after two increments is `12`, but the actual result
is `11`.

One update is lost.

The problem is that both threads can execute the critical section
simultaneously.

We need a mechanism that coordinates their access.

This is the basic idea behind **mutual exclusion**.

### The desired behavior

``` text
Thread A enters critical section
        |
Thread A executes protected code
        |
Thread A leaves critical section
        |
Thread B enters critical section
        |
Thread B executes protected code
        |
Thread B leaves critical section
```

## 3. Four Important Properties of a Critical Section

There are four concepts worth understanding.

### A. Mutual Exclusion

Only one thread at a time can execute a particular protected section
when using a mutual-exclusion mechanism.

For example:

If Thread A is modifying a shared bank balance, Thread B must wait
before entering the same protected section.

**Important:** Mutual exclusion applies to threads competing for the
same lock. It does not mean only one thread can execute the entire
application.

### B. Progress

If no thread is currently inside a protected section, and some threads
want to enter, the system should allow one of them to proceed.

In other words, the system shouldn't unnecessarily prevent all threads
from entering.

### C. Bounded Waiting

A thread waiting to enter a critical section should not be postponed
indefinitely.

Otherwise, one thread might continuously get access while another waits
forever.

This is related to starvation, which we will study in Lesson 33.

**Note:** These are classical critical-section problem requirements.
Java's ordinary `synchronized` mechanism provides mutual exclusion, but
you should not assume it guarantees strict FIFO ordering or bounded
waiting.

### D. Correct Scope

The protected section must include the complete operation that needs
coordination.

Consider:

``` java
if (balance >= 500) {
    balance -= 500;
}
```

You cannot safely protect only:

``` java
balance -= 500;
```

The check and the deduction belong to one logical operation.

Otherwise, two threads might both check the balance before either
deducts money.

This is an example of a **check-then-act** operation.

## 4. Critical Section vs. Normal Code

Not every line in a method is a critical section.

Consider:

``` java
public class BookingService {

    private int availableSlots = 5;

    public void bookSlot() {

        System.out.println("Booking started");

        availableSlots--;

        System.out.println("Booking completed");
    }
}
```

Let's classify the operations:

  -----------------------------------------------------------------------
  Operation                           Critical section?
  ----------------------------------- -----------------------------------
  Print booking started               No, assuming no shared mutable
                                      logging state is involved

  Decrease `availableSlots`           Yes

  Print booking completed             No, under the same assumption
  -----------------------------------------------------------------------

The critical section is:

``` java
availableSlots--;
```

However, real applications often have multiple related operations that
must be protected together.

For example:

``` java
if (availableSlots > 0) {
    availableSlots--;
    bookingCount++;
}
```

The entire check-and-update sequence is the critical section because
these operations collectively maintain an invariant.

An **invariant** is a condition that must remain true for the system to
be correct.

For example:

``` text
availableSlots >= 0
```

If you protect only the decrement but not the availability check, your
system may still be incorrect.

## 5. How Java Protects a Critical Section

Java provides several mechanisms to coordinate access to critical
sections.

We will study each in detail in later lessons.

  Mechanism          Purpose
  ------------------ ----------------------------------------------
  `synchronized`     Mutual exclusion and visibility guarantees
  `ReentrantLock`    Explicit lock-based coordination
  `AtomicInteger`    Provides atomic operations on integer values
  `Semaphore`        Limits concurrent access to a resource
  Database locking   Coordinates conflicting database operations

For now, let's preview `synchronized`:

``` java
public class Counter {

    private int count = 0;

    public synchronized void increment() {
        count++;
    }

    public int getCount() {
        return count;
    }
}
```

What happens here?

-   Thread A enters `increment()` and acquires the object's intrinsic
    lock.
-   Thread B attempts to enter the same synchronized method on the same
    object.
-   Thread B waits until Thread A releases the lock.
-   Thread B then acquires the lock and executes.

Now the increments are coordinated.

We'll properly learn `synchronized` in Phase 3.

**Remember:** Synchronization only works as intended when competing
operations use the same lock. Synchronizing unrelated objects does not
protect the same shared data.

## 6. Critical Sections in the Turf Project

Let's use a real booking example.

Suppose your turf has one available slot.

Two customers attempt to book it simultaneously.

Your application might execute:

``` java
public void bookSlot(Long slotId) {

    Slot slot = slotRepository.findById(slotId)
            .orElseThrow();

    if (slot.getAvailable()) {

        slot.setAvailable(false);

        slotRepository.save(slot);
    }
}
```

What's wrong?

Two requests might:

1.  Read the same slot.
2.  Both see `available = true`.
3.  Both proceed with booking.
4.  Both attempt to save their booking.

This is a critical-section problem.

But here's an important engineering distinction:

**A Java critical section and a database critical section are not
necessarily the same thing.**

In a Spring Boot application, multiple requests can execute on different
threads, and multiple application instances can run on different
machines.

A Java `synchronized` block only coordinates threads sharing the
relevant lock in the same JVM.

For Turf, you'll eventually need database-level protection too, such as
transactions, constraints, and appropriate locking.

We'll learn those in Phase 6.

## 7. Common Interview Questions

### Q1. What is a critical section?

A section of code that accesses shared mutable resources and requires
coordinated execution to maintain correctness.

### Q2. What is mutual exclusion?

A property that ensures only one thread at a time can enter a particular
protected section using the same mutual-exclusion mechanism.

### Q3. Is every shared variable a critical section?

No. A critical section is code that accesses shared resources in a way
that requires coordination. For example, concurrent read-only access to
immutable data generally doesn't require mutual exclusion.

### Q4. Can a critical section contain multiple statements?

Yes. In fact, it often needs to contain multiple statements to protect a
complete logical operation.

### Q5. What happens if a critical section is too large?

-   Threads wait longer.
-   Lock contention increases.
-   Throughput may decrease.
-   Application performance can suffer.

### Q6. What happens if a critical section is too small?

You might fail to protect the complete logical operation, leaving race
conditions possible.

### Q7. Can two threads execute the same critical section simultaneously?

If both use the same correctly implemented mutual-exclusion lock, no.
Without appropriate coordination, they can.

## 9. Knowledge Check

1.  What is the critical section in the withdrawal example?
    -   The balance check and deduction together.
2.  What is mutual exclusion?
    -   Allowing only one competing thread into a protected section at a
        time.
3.  Can two threads execute the same critical section simultaneously
    without synchronization?
    -   Yes, they can.
4.  Why shouldn't a critical section be unnecessarily large?
    -   It increases lock contention and waiting.

## 10. Important Things to Remember

1.  A critical section is code that accesses shared mutable resources
    and requires coordination.
2.  Mutual exclusion prevents competing threads using the same lock from
    entering the protected section simultaneously.
3.  The complete logical operation must be protected, not just one
    statement within it.
4.  The classical critical-section problem includes mutual exclusion,
    progress, and bounded waiting.
5.  A critical section can contain multiple statements.
6.  An invariant is a condition that must remain true for the system to
    be correct.
7.  `synchronized` is one Java mechanism for protecting critical
    sections.
8.  Competing operations must use the same lock for that lock to
    coordinate them.
9.  Java thread synchronization does not automatically coordinate
    multiple application instances or database transactions.
10. Real booking systems need appropriate database-level protection as
    well.
