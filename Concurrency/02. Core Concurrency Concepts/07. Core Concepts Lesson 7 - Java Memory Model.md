# Core Concepts - Phase 2, Lesson 7: Java Memory Model (JMM)

<br>
<br>

## 1. First, What Problem Is the JMM Solving?

Imagine two people working with the same notebook.

-   Person A writes `ready = true`.
-   Person B checks whether `ready` is true.

You might assume Person B will always see the latest value as soon as
Person A writes it.

But computers and programming languages use performance optimizations. A
thread's memory operations do not automatically behave as though every
access is instantly and globally synchronized with every other thread.

Java therefore needs clear rules for questions such as:

-   When must one thread see another thread's write?
-   Which operations are allowed to appear in a different order?
-   What guarantees do locks and `volatile` provide?
-   What behavior may a program rely on when multiple threads access
    shared data?

The Java Memory Model defines those rules.

<br>

## 2. What Is the Java Memory Model?

The **Java Memory Model (JMM)** is the set of rules that defines how
threads interact through memory.

In simpler words:

**The JMM tells us what one thread is allowed to see when another thread
reads or changes shared data. It also defines the ordering guarantees
between memory operations.**

The JMM is part of the Java language and platform specifications. It
gives Java programs consistent rules across different hardware and
runtime implementations.

The JMM mainly helps us reason about three things:

1.  **Visibility** --- whether a thread can see another thread's
    changes.
2.  **Ordering** --- which memory operations must be observed before
    others.
3.  **Atomicity guarantees** --- which individual operations are
    indivisible under the memory model.

Important: the JMM is not a setting that you turn on. It is the set of
rules Java uses when defining concurrent program behavior.

<br>

## 3. Does Every Thread Have Its Own Memory?

You may hear explanations that say:

-   Each thread has its own memory.
-   Threads share main memory.
-   A thread may keep values in a local cache.

These descriptions can be useful as a simplified mental picture, but
they are not a literal map of Java's memory architecture.

Let's use a careful model.

<br>

### A simplified picture

```
                 SHARED JAVA OBJECT
                 +---------------+
                 |               |
                 |  int count    |
                 |  boolean ready|
                 |               |
                 +---------------+
                    /         \
                   /           \
                  v             v
             +---------+   +---------+
             | Thread A|   | Thread B|
             +---------+   +---------+
                  |             |
                  |             |
              Reads and      Reads and
               writes         writes
                  |             |
                  +------+------+
                         |
                         v
              JVM and CPU may use
              performance optimizations
                         |
                         v
                JAVA MEMORY MODEL
                         |
                         v
          Defines the rules and guarantees
          for how threads see each other's
          changes and memory operations
```

<br>

### Important clarification

The JMM does not say that every Java thread literally owns a private
copy of every variable.

It also does not require every variable to be physically stored in a CPU
cache.

The actual implementation may involve registers, CPU caches, memory,
compiler transformations, and other mechanisms.

For writing correct concurrent Java code, focus on the guarantees
provided by the JMM rather than trying to predict the exact hardware
behavior.

<br>

## 4. A Simple Example: Two Threads Sharing a Variable

Consider:

``` java
public class SharedFlag {

    static boolean ready = false;

    public static void main(String[] args) {

        Thread reader = new Thread(() -> {
            while (!ready) {
                // Wait for ready to become true
            }

            System.out.println("Ready!");
        });

        reader.start();

        ready = true;
    }
}
```

What do we expect?

1.  The reader thread checks `ready`.
2.  The main thread changes `ready` to `true`.
3.  The reader thread sees `true`.
4.  The loop ends and prints `Ready!`.

But the code does not establish a visibility guarantee between the write
and the reader's reads.

The reader is not guaranteed to observe the main thread's update.

This is not a correct way to coordinate threads.

<br>

### A version with `volatile`

``` java
public class SharedFlag {

    static volatile boolean ready = false;

    public static void main(String[] args) {

        Thread reader = new Thread(() -> {
            while (!ready) {
                // Wait for ready to become true
            }

            System.out.println("Ready!");
        });

        reader.start();

        ready = true;
    }
}
```

The `volatile` declaration establishes the required visibility and
ordering guarantees for this flag.

The reader's subsequent volatile reads observe the write to `true` or a
later write in the volatile synchronization order.

For a simple stop or ready flag, this is a common use of `volatile`.

We will study `volatile` in detail in Phase 3.

## 5. The JMM and Visibility

Let's connect the JMM to the previous lesson.

Suppose:

``` java
class SharedData {
    int number = 0;
}
```

Thread A:

``` java
sharedData.number = 100;
```

Thread B:

``` java
System.out.println(sharedData.number);
```

If these threads access the same object without a suitable
synchronization relationship, Thread B is not guaranteed to see `100`.

It may observe an earlier value.

This is a visibility problem.

The JMM defines when a write by one thread is guaranteed to be visible
to a read by another thread.

Some mechanisms that establish visibility guarantees include:

-   A write to a `volatile` field followed by a subsequent read of that
    same field.
-   Releasing a monitor with `synchronized`, followed by another thread
    acquiring that same monitor.
-   Other concurrency utilities whose specifications define
    synchronization and memory-consistency effects.

The important idea is that **visibility needs a guarantee**. It should
not be based on hope, timing, or the fact that a program appeared to
work during testing.

<br>

## 6. The JMM and Instruction Reordering

Now let's understand another important idea: ordering.

Consider:

``` java
int number = 0;
boolean ready = false;
```

Thread A:

``` java
number = 42;
ready = true;
```

Thread B:

``` java
if (ready) {
    System.out.println(number);
}
```

A developer reads Thread A's code from top to bottom:

1.  Set `number` to `42`.
2.  Set `ready` to `true`.

So the developer may expect that if Thread B sees `ready == true`, it
must also see `number == 42`.

But without a synchronization relationship, that conclusion is not
guaranteed.

The compiler and runtime may perform optimizations, and the JMM allows
certain reorderings as long as the required Java semantics are
preserved.

This does not mean the compiler can freely reorder every operation. It
must obey the JMM.

The problem is that unsynchronized threads cannot assume that the order
they see is always the same as the source-code order in another thread.

<br>

### A useful mental model

Source code:

``` java
number = 42;
ready = true;
```

What the programmer wants:

``` text
Write number
    happens before
Write ready
```

But another thread cannot rely on observing that relationship unless the
program establishes the appropriate synchronization.

<br>

### A version using `volatile`

``` java
class Message {

    int number = 0;
    volatile boolean ready = false;

    void publish() {
        number = 42;
        ready = true;
    }

    void consume() {
        if (ready) {
            System.out.println(number);
        }
    }
}
```

If one thread calls `publish()` and another thread subsequently reads
`ready` as `true` in `consume()`, the volatile write/read relationship
provides the required ordering and visibility for the earlier write to
`number`.

The reader can therefore rely on seeing `number == 42`, assuming no
later write changes it.

Notice something important:

`number` itself is not volatile in this example. The synchronization
relationship created by the volatile field also makes the earlier write
to `number` visible to the reader.

This is a first look at the happens-before concept. We'll study it
carefully in the next lesson.

<br>

## 7. What Is a Data Race?

A **data race** occurs when two or more threads access the same variable
concurrently, at least one access is a write, and the accesses are not
ordered by a happens-before relationship.

In simpler words:

A data race happens when threads access the same shared data, one or
more of them modify it, and the program has not established the required
ordering between those accesses.

Example:

``` java
class Counter {

    int count = 0;

    void increment() {
        count++;
    }
}
```

If two threads call `increment()` on the same `Counter` object, they
access and modify the same field without synchronization.

There is a data race.

This can lead to lost updates and other incorrect behavior.

<br>

### Data race versus race condition

These terms are related, but they are not identical.

```
  Term                                Meaning
  ----------------------------------- -----------------------------------
  Data race                           A specific memory-access situation:
                                      conflicting concurrent accesses
                                      without a happens-before ordering

  Race condition                      A broader program-correctness
                                      problem where the result depends on
                                      the timing or ordering of
                                      operations
```


A program can have a race condition even when its individual memory
accesses are properly synchronized. For example, a sequence of
individually thread-safe operations may still be logically incorrect if
another thread can change the state between them.

For now, remember:

-   A data race is a JMM-related concept.
-   A race condition is a broader correctness concept.

<br>

## 8. What Does the JMM Guarantee About `synchronized`?

Consider:

``` java
class SharedData {

    private int value = 0;

    public synchronized void write() {
        value = 100;
    }

    public synchronized int read() {
        return value;
    }
}
```

Both methods are instance synchronized methods.

They use the monitor associated with the same `SharedData` object.

The JMM gives an important guarantee:

**An unlock of a monitor happens-before every subsequent lock of that
same monitor.**

In simpler words:

1.  Thread A enters `write()` and acquires the object's lock.
2.  Thread A writes `value = 100`.
3.  Thread A exits the method and releases the lock.
4.  Thread B later enters `read()` and acquires that same object's lock.
5.  Thread B is guaranteed to see the write made before Thread A
    released the lock.

This is why synchronization provides both:

-   Mutual exclusion for code using the same monitor.
-   Visibility and ordering guarantees.

Important: both threads must coordinate through the same monitor.
Locking different objects does not establish this relationship.

<br>

## 9. What Does the JMM Guarantee About `volatile`?

Consider:

``` java
class SharedData {

    private volatile int value = 0;

    public void write() {
        value = 100;
    }

    public int read() {
        return value;
    }
}
```

A write to a volatile field happens-before subsequent reads of that same
field in the volatile synchronization order.

In practical terms:

-   When a thread writes `100` to `value`,
-   A subsequent thread reading that volatile field gets the visibility
    and ordering guarantees required by the JMM.

But remember:

``` java
value++;
```

is still not an atomic increment merely because `value` is volatile.

The JMM provides visibility and ordering guarantees for volatile access.
It does not turn a compound read-modify-write sequence into one
indivisible operation.

<br>

## 10. Important JMM Rules to Remember

At this stage, learn these rules at a high level:

1.  **Program order:** Within a single thread, actions are ordered
    according to the program-order rules of the JMM.
2.  **Monitor rule:** An unlock of a monitor happens-before a subsequent
    lock of that same monitor.
3.  **Volatile rule:** A write to a volatile field happens-before a
    subsequent read of that same field in the synchronization order.
4.  **Thread-start rule:** A call to `Thread.start()` happens-before any
    action in the started thread.
5.  **Thread-termination rule:** All actions in a thread happen-before
    another thread successfully detects that the thread has terminated,
    for example through a successful `join()`.
6.  **Transitivity:** If action A happens-before action B, and action B
    happens-before action C, then A happens-before C.

These are examples of happens-before rules. The next lesson will explain
the relationship in detail and show how to use it when reasoning about
concurrent code.

## 11. Why `Thread.sleep()` Does Not Fix JMM Problems

Consider:

``` java
while (!ready) {
    Thread.sleep(100);
}
```

Some developers think sleeping gives another thread time to update
`ready`, so the problem is solved.

It is not.

`Thread.sleep()` pauses the current thread for a period of time. It does
not establish a happens-before relationship with another thread and does
not guarantee visibility of that thread's writes.

Time passing is not a synchronization mechanism.

Use an appropriate mechanism such as:

-   `volatile` for a simple shared flag.
-   `synchronized` for coordinated access to shared state.
-   A concurrency utility designed for the task, such as a latch or
    blocking queue.

We'll study these tools later in the roadmap.

## 12. How This Relates to Spring Boot

Spring Boot applications often handle many requests concurrently.

For example:

``` java
@Service
public class AppSettingsService {

    private boolean maintenanceMode = false;

    public void enableMaintenanceMode() {
        maintenanceMode = true;
    }

    public boolean isMaintenanceMode() {
        return maintenanceMode;
    }
}
```

A Spring service is commonly a singleton within its application context.

That means multiple request-handling threads may call methods on the
same service object.

The `maintenanceMode` field is shared mutable state.

Without suitable synchronization, the code does not establish a
visibility guarantee between a thread that changes the field and another
thread that reads it.

For a simple in-memory flag inside one JVM, you could use:

``` java
private volatile boolean maintenanceMode = false;
```

But do not assume this solves every backend problem.

If your application has several Spring Boot instances, each instance has
its own JVM and its own copy of this field.

A volatile field in one instance does not update the field in another
instance.

For system-wide settings, you may need a shared source of truth, such as
a database or a distributed configuration mechanism.

## 13. How This Relates to the Turf Booking System

Imagine your Turf application has a booking switch:

``` text
bookingEnabled = true
```

An administrator disables bookings.

At the same time, customers are sending booking requests.

There are two separate questions:

### Question A: Does every request thread in one JVM see the updated setting?

This is a visibility and JMM question.

For a simple in-memory flag, `volatile` may provide the needed
visibility among threads in that JVM.

### Question B: Do all running application instances see the same setting?

This is not solved by Java's in-memory JMM mechanisms alone.

If you run three application instances, each has its own memory.

You need a shared system-wide source of truth or a mechanism to
distribute the update.

### What about preventing double booking?

The JMM does not automatically protect your database booking workflow.

Suppose two customers request the same turf slot.

Both requests may:

1.  Read the slot as available.
2.  Decide that it can be booked.
3.  Attempt to create a booking.

Even if some Java fields are volatile, that does not make the complete
database operation safe.

For a real booking system, you must coordinate the complete booking
operation at the correct boundary, typically with database transactions,
constraints, conditional updates, or locking.
