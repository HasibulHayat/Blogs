# Core Concepts --- Phase 2, Lesson 6: Data Visibility

## Introduction

In the previous lessons, we covered:

-   Shared data and shared mutable state
-   Race conditions
-   Critical sections
-   Atomicity
-   Thread safety

Now we'll study another major concurrency problem:

**Data visibility**

So far, we've focused on what happens when threads interfere with one
another while updating shared data. But there is another question:

**When one thread changes a value, how and when does another thread see
that change?**

This lesson explains visibility, why threads may observe stale values,
how Java provides visibility guarantees, and why this matters in a
Spring Boot backend and the Turf project.

------------------------------------------------------------------------

## 1. What Is Data Visibility?

Data visibility describes whether a change made by one thread becomes
observable to another thread.

Imagine two threads sharing a variable:

``` java
public class SharedData {

    private boolean ready = false;
}
```

Thread A changes `ready` to `true`.

Thread B reads `ready`.

We might expect Thread B to see `true` immediately. But without an
appropriate visibility guarantee, Java does not promise that Thread B
will observe the latest value simply because Thread A performed the
write.

Thread B may continue to observe an older value.

This is called a **visibility problem** or **stale read**.

The important point:

A thread's update being performed does not, by itself, guarantee that
another thread will observe that update.

## 2. Why Can a Visibility Problem Happen?

Modern computers and JVMs use optimizations to improve performance.

Relevant mechanisms include:

-   CPU caches
-   CPU registers
-   Compiler optimizations
-   Instruction reordering
-   Memory access optimizations

A thread may work with values in ways that do not require every read and
write to immediately behave like a direct, globally synchronized access
to main memory.

The Java Memory Model (JMM) defines the rules for how threads interact
through memory. It determines which memory effects are guaranteed to be
visible to other threads.

For now, you do not need to understand every internal CPU detail.
Remember:

**Without a proper synchronization relationship, one thread is not
guaranteed to see another thread's latest write.**

## 3. A Classic Visibility Problem

Consider this example:

``` java
public class VisibilityExample {

    private static boolean running = true;

    public static void main(String[] args)
            throws InterruptedException {

        Thread worker = new Thread(() -> {
            while (running) {
                // Keep working while running is true
            }

            System.out.println("Worker stopped");
        });

        worker.start();

        Thread.sleep(1000);

        running = false;

        System.out.println("Main thread changed running to false");
    }
}
```

What do we expect?

1.  The worker thread starts.
2.  It repeatedly checks `running`.
3.  The main thread changes `running` to `false`.
4.  The worker sees `false` and exits the loop.

But the program has a visibility problem.

Because `running` is an ordinary, non-volatile field and the threads do
not use another synchronization mechanism to coordinate access, the
worker is not guaranteed to observe the main thread's update.

The worker may continue looping.

The exact behavior can depend on runtime optimizations and execution
conditions. Do not rely on a particular outcome from a single run.

## 4. What Is a Stale Read?

A stale read happens when a thread observes an older value rather than a
more recent update made by another thread.

Example:

``` java
private int value = 10;
```

Suppose:

-   Thread A changes `value` from `10` to `20`.
-   Thread B reads `value`.

If there is no appropriate visibility guarantee, Thread B is not
guaranteed to observe `20`.

It may observe `10`.

This is a visibility issue.

Notice the difference from a lost update:

  -----------------------------------------------------------------------
  Problem                             What goes wrong?
  ----------------------------------- -----------------------------------
  Lost update                         Concurrent writes overwrite one
                                      another, so an update is lost

  Stale read                          A thread does not observe another
                                      thread's more recent write
  -----------------------------------------------------------------------

These are different problems, although a program can suffer from both.

## 5. Visibility Is Different from Atomicity

Atomicity and visibility are related concurrency concepts, but they
solve different problems.

  Concept      Main question
  ------------ ---------------------------------------------------
  Atomicity    Does an operation happen as one indivisible unit?
  Visibility   Does a thread see another thread's update?

Example of an atomicity problem:

``` java
count++;
```

Two threads may both read the same old value and overwrite one another's
increments.

Example of a visibility problem:

``` java
while (running) {
    // Work
}
```

One thread sets `running` to `false`, but another thread is not
guaranteed to observe the change.

A program can have an atomicity problem, a visibility problem, or both.

## 6. How Java Provides Visibility Guarantees

Java provides several mechanisms that can establish visibility
guarantees between threads.

At this stage, focus on the main ideas:

1.  `volatile`
2.  `synchronized`
3.  Other synchronization mechanisms that establish a happens-before
    relationship

We will study these mechanisms in more depth in later lessons.

### 6.1 The `volatile` Keyword

A field declared `volatile` has special visibility and ordering
guarantees under the Java Memory Model.

Example:

``` java
public class VisibilityExample {

    private static volatile boolean running = true;

    public static void main(String[] args)
            throws InterruptedException {

        Thread worker = new Thread(() -> {
            while (running) {
                // Keep working while running is true
            }

            System.out.println("Worker stopped");
        });

        worker.start();

        Thread.sleep(1000);

        running = false;

        System.out.println("Main thread changed running to false");
    }
}
```

The important change is:

``` java
private static volatile boolean running = true;
```

Now, when the main thread writes `false`, the volatile rules ensure that
a subsequent read of `running` by the worker observes the write or a
later write in the synchronization order.

For this simple stop flag, `volatile` is an appropriate solution.

We will study `volatile` in detail in Phase 3, Lesson 29.

### 6.2 Synchronization

Java's `synchronized` keyword provides both mutual exclusion and memory
visibility guarantees.

Example:

``` java
public class SharedData {

    private int value = 0;

    public synchronized void update() {
        value = 100;
    }

    public synchronized int read() {
        return value;
    }
}
```

When one thread exits a synchronized block or method protected by a
particular monitor, its actions before releasing that monitor
happen-before a subsequent successful lock of the same monitor by
another thread.

In practical terms, if Thread A updates `value` while holding the
object's monitor and then releases it, Thread B can acquire that same
monitor and see the update.

The same lock must be used for the coordination to work.

We will study synchronized methods, blocks, and monitors in Phase 3.

## 7. Important: `volatile` Does Not Make Everything Thread-Safe

Consider:

``` java
public class Counter {

    private volatile int count = 0;

    public void increment() {
        count++;
    }
}
```

Does `volatile` make this counter thread-safe?

**No.**

`volatile` provides visibility and ordering guarantees for accesses to
the field. It does not make the complete read-modify-write operation
atomic.

Two threads can still:

1.  Read the same value.
2.  Calculate the same incremented value.
3.  Write the same result.

One update can be lost.

For concurrent increments, use a suitable mechanism such as
`AtomicInteger` or synchronization.

Remember:

-   `volatile` helps with visibility and ordering.
-   `volatile` does not provide mutual exclusion.
-   `volatile` does not make `count++` atomic.

## 8. Visibility and the Java Memory Model

The **Java Memory Model (JMM)** is the part of the Java specification
that defines how threads interact through memory.

It describes guarantees involving:

-   Visibility of writes
-   Ordering of memory operations
-   Synchronization between threads
-   The happens-before relationship

The JMM does not require you to reason directly about a particular CPU's
cache implementation.

Instead, it defines the guarantees that Java programs can rely on,
regardless of the underlying hardware, when the program follows the
memory model's rules.

For this lesson, remember:

**Visibility is governed by the Java Memory Model, and synchronization
mechanisms establish guarantees about what one thread can observe from
another.**

We'll study the JMM and happens-before relationship in dedicated lessons
later in Phase 2.

## 9. Visibility in a Spring Boot Application

Imagine a Spring service:

``` java
@Service
public class MaintenanceService {

    private boolean maintenanceMode = false;

    public void enableMaintenanceMode() {
        maintenanceMode = true;
    }

    public boolean isMaintenanceMode() {
        return maintenanceMode;
    }
}
```

Spring services are commonly singleton-scoped by default. That means
multiple request-handling threads may call methods on the same service
instance.

One request thread may call:

``` java
maintenanceService.enableMaintenanceMode();
```

Another request thread may call:

``` java
maintenanceService.isMaintenanceMode();
```

If the field is shared and mutable, you must consider how the update
becomes visible to the reading thread.

The code above does not establish a visibility guarantee by itself.

For a simple in-memory flag shared among threads in one JVM, a
`volatile` field may be appropriate:

``` java
@Service
public class MaintenanceService {

    private volatile boolean maintenanceMode = false;

    public void enableMaintenanceMode() {
        maintenanceMode = true;
    }

    public boolean isMaintenanceMode() {
        return maintenanceMode;
    }
}
```

This example assumes the flag is only an in-memory setting within one
application instance.

If the application runs multiple Spring Boot instances, each instance
has its own field and its own JVM memory. A volatile field in one
instance does not update the field in another instance.

For application-wide maintenance mode, you may need shared storage or a
configuration/distribution mechanism.

## 10. Visibility in the Turf Project

Imagine an administrator temporarily disables bookings.

A simplified service contains:

``` java
@Service
public class BookingSettingsService {

    private boolean bookingEnabled = true;

    public void disableBookings() {
        bookingEnabled = false;
    }

    public boolean canAcceptBooking() {
        return bookingEnabled;
    }
}
```

Potential situation:

1.  An administrator disables bookings through one request.
2.  Another request checks whether bookings are enabled.
3.  Both requests are handled by different threads.
4.  The reading thread is not guaranteed to observe the latest update
    with the code as written.

For a single JVM and a simple in-memory flag, `volatile` could provide
the required visibility:

``` java
private volatile boolean bookingEnabled = true;
```

But consider the bigger Turf architecture:

-   You may run multiple application instances.
-   You may deploy multiple servers.
-   Booking settings may need to persist across application restarts.
-   Other services may need to read the same setting.

In that case, an in-memory volatile field is not enough to provide
system-wide consistency.

A shared source of truth, such as a database or distributed
configuration mechanism, may be needed.

This illustrates a recurring backend principle:

**Choose a concurrency mechanism that matches the scope of the shared
state.**

## 11. Common Interview Questions

### Q1. What is visibility in Java concurrency?

Visibility means that a change made by one thread becomes observable to
another thread under the guarantees provided by the Java Memory Model.

### Q2. What is a stale read?

A stale read occurs when a thread observes an older value instead of a
more recent write made by another thread.

### Q3. Why can a thread fail to see another thread's update?

Without an appropriate synchronization relationship, the Java Memory
Model does not guarantee that the reading thread will observe the latest
write.

### Q4. How does `volatile` help?

A volatile write and subsequent volatile reads of the same field have
visibility and ordering guarantees defined by the Java Memory Model.

### Q5. Does `volatile` make `count++` atomic?

No. It does not make compound read-modify-write operations atomic.

### Q6. Does `synchronized` provide visibility?

Yes. Releasing a monitor happens-before a subsequent acquisition of the
same monitor, providing the required visibility and ordering guarantees.

### Q7. What is the difference between visibility and atomicity?

Visibility concerns whether a thread sees another thread's update.
Atomicity concerns whether an operation is indivisible.

### Q8. Is a volatile field shared between multiple Spring Boot instances?

No. Each JVM has its own memory. A volatile field coordinates visibility
among threads in one JVM, not across separate application instances.

### Q9. Is `Thread.sleep()` a visibility mechanism?

No. Sleeping does not establish a happens-before relationship and does
not guarantee that another thread's changes become visible.

## 12. Practical Exercise

Create a class with a shared boolean flag:

``` java
public class SharedFlag {

    private boolean running = true;

    public void startWorker() {

        Thread worker = new Thread(() -> {
            while (running) {
                // Keep running
            }

            System.out.println("Worker stopped");
        });

        worker.start();
    }

    public void stopWorker() {
        running = false;
    }
}
```

Then:

1.  Start the worker thread.
2.  Wait for a short period in the main thread.
3.  Call `stopWorker()`.
4.  Observe whether the worker exits.
5.  Change `running` to `volatile`.
6.  Run the program again and explain why the volatile declaration
    changes the visibility guarantees.

Answer these questions:

1.  Which variable is shared?
2.  Which thread writes to it?
3.  Which thread reads it?
4.  What is a stale read?
5.  Why does `Thread.sleep()` not solve the visibility problem?
6.  Why is `volatile` suitable for this simple stop flag?
7.  Would `volatile` be enough if the worker needed to increment a
    shared counter safely?

Note: The program without `volatile` may appear to work on some machines
or runs. That does not mean the code has a valid visibility guarantee.
The purpose is to understand the memory-model issue, not to rely on
reproducing a hang every time.
