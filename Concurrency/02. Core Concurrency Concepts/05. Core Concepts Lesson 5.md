# Core Concepts --- Phase 2, Lesson 5: Thread Safety

## Introduction

In the previous lessons, we covered:

-   Shared data and shared mutable state
-   Race conditions
-   Critical sections
-   Atomicity

Now we'll connect those ideas and study one of the most important
concepts in concurrent programming:

**Thread safety**

Thread safety is about whether a class, object, or piece of code
continues to behave correctly when multiple threads access it
concurrently.

This lesson covers what thread safety means, why shared mutable state
creates risks, common ways to make code thread-safe, and how these ideas
apply to the Turf booking system.

------------------------------------------------------------------------

## 1. What Is Thread Safety?

A component is **thread-safe** when it behaves correctly under
concurrent access, according to its intended behavior and contract.

In simpler words:

If multiple threads use the same object at the same time, the object
should still produce correct and consistent results.

Consider a counter shared by multiple threads.

``` java
public class Counter {

    private int count = 0;

    public void increment() {
        count++;
    }

    public int getCount() {
        return count;
    }
}
```

If several threads call `increment()` at the same time, updates can be
lost because `count++` is not atomic.

This implementation is not thread-safe for concurrent increments.

The problem is not that multiple threads exist. The problem is that they
access and modify shared mutable state without appropriate coordination.

## 2. The Three Ingredients That Often Create Thread-Safety Problems

A common source of concurrency bugs has three ingredients:

1.  **Shared data** --- multiple threads can access the same data.
2.  **Mutable data** --- the data can change.
3.  **Concurrent access** --- multiple threads may access or modify it
    at overlapping times.

Example:

``` java
public class Counter {

    private int count = 0;

    public void increment() {
        count++;
    }
}
```

-   `count` is shared when multiple threads use the same `Counter`
    object.
-   `count` is mutable because its value changes.
-   Multiple threads can call `increment()` concurrently.

These conditions create the possibility of a race condition.

This is a useful way to identify risk, but it is not a complete formal
test: thread safety also depends on the operations, invariants,
visibility, and coordination guarantees involved.

## 3. What Does Correct Behavior Mean?

Thread safety is not simply about preventing exceptions.

A thread-safe component must preserve its intended rules, even when
operations overlap.

Suppose a bank account has a balance of 1,000 taka.

Two threads attempt these withdrawals:

-   Thread A withdraws 700.
-   Thread B withdraws 500.

The account must not allow both withdrawals to succeed, because together
they require 1,200 taka.

The important rule, or **invariant**, is:

``` text
The account balance must never become negative.
```

A correct implementation must preserve that rule during concurrent
operations.

A program that does not crash but produces an invalid balance is still
incorrect and not thread-safe.

## 4. A Non-Thread-Safe Example

Consider this simplified bank account:

``` java
public class BankAccount {

    private int balance = 1000;

    public void withdraw(int amount) {

        if (balance >= amount) {
            balance = balance - amount;
        }
    }

    public int getBalance() {
        return balance;
    }
}
```

Now imagine two threads call `withdraw()` on the same account:

-   Thread A requests 700.
-   Thread B requests 500.

A possible interleaving is:

    Step Thread A                    Thread B
  ------ --------------------------- ---------------------------
       1 Reads balance: 1000         
       2                             Reads balance: 1000
       3 Checks 1000 \>= 700: true   
       4                             Checks 1000 \>= 500: true
       5 Calculates 300              
       6                             Calculates 500
       7 Writes balance = 300        
       8                             Writes balance = 500

Both withdrawals may appear to succeed, and the final balance may be
500.

That result is incorrect: the system has effectively lost one
withdrawal.

The problem is that the check and update form one logical operation, but
the implementation does not coordinate that complete operation.

## 5. Common Ways to Achieve Thread Safety in Java

There is no single solution that fits every situation. The right
approach depends on the data, operations, performance requirements, and
where the shared state lives.

### 5.1 Immutability

An immutable object cannot be changed after it is created.

If an object has no mutable state that threads can interfere with,
sharing it is often much safer.

Example:

``` java
public final class UserProfile {

    private final String name;
    private final int age;

    public UserProfile(String name, int age) {
        this.name = name;
        this.age = age;
    }

    public String getName() {
        return name;
    }

    public int getAge() {
        return age;
    }
}
```

This class:

-   Is `final`, so it cannot be subclassed.
-   Has `private final` fields.
-   Does not expose setters.
-   Does not provide a way to change its state after construction.

For this example, the fields are immutable values (`String` and `int`).

Be careful: a `final` reference does not make the referenced object
immutable. If a class contains a mutable `List`, for example, callers
may still be able to modify that list unless the class protects or
defensively copies it.

Immutability is a powerful way to reduce shared mutable state.

### 5.2 Synchronization

Java's `synchronized` keyword can coordinate access to a critical
section.

``` java
public class Counter {

    private int count = 0;

    public synchronized void increment() {
        count++;
    }

    public synchronized int getCount() {
        return count;
    }
}
```

For calls made on the same object, these instance synchronized methods
use that object's monitor lock.

Only one thread at a time can hold that monitor.

This prevents concurrent execution of these synchronized instance
methods on the same object.

Important: synchronization works only when competing threads coordinate
using the same lock. Synchronizing on different objects does not protect
the same shared data from one another.

We will study synchronized methods, blocks, monitors, and locks in Phase
3.

### 5.3 Atomic Classes

Java provides atomic classes for supported operations on individual
values.

Example:

``` java
import java.util.concurrent.atomic.AtomicInteger;

public class Counter {

    private final AtomicInteger count = new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet();
    }

    public int getCount() {
        return count.get();
    }
}
```

The increment operation is atomic, so concurrent increments do not
overwrite one another.

However, an atomic field does not automatically make every multi-step
operation in a class thread-safe.

If correctness depends on a condition and a later update, you must
ensure that the complete logical operation is coordinated.

We'll study atomic classes and compare-and-set in Phase 4.

### 5.4 Concurrent Collections

Java provides collections designed for concurrent access, such as:

-   `ConcurrentHashMap`
-   `CopyOnWriteArrayList`
-   `BlockingQueue` implementations

These are useful when multiple threads need to access shared collection
data.

For example, a normal `HashMap` is not designed for unsynchronized
concurrent modification by multiple threads. A `ConcurrentHashMap`
provides concurrency-aware operations.

But using a concurrent collection does not automatically make a sequence
of operations atomic.

For example:

``` java
if (!map.containsKey(key)) {
    map.put(key, value);
}
```

The combined check-then-act sequence may still race with another thread.

Use an appropriate atomic collection operation, such as `putIfAbsent`,
when it matches the required behavior.

We'll study concurrent collections in Phase 4.

## 6. Thread Safety Is Not the Same as Synchronizing Everything

A common beginner mistake is to add `synchronized` to every method.

That is not automatically a good design.

Excessive synchronization can:

-   Reduce concurrency.
-   Increase waiting time.
-   Create lock contention.
-   Make deadlocks more likely if locks are acquired inconsistently.
-   Make code harder to reason about.

The goal is not to stop threads from running concurrently.

The goal is to coordinate only the operations that need coordination,
while preserving correctness.

For example, a method that only reads an immutable field may not need
synchronization at all.

## 7. Thread Safety Has Different Scopes

It is important to understand where the shared state exists.

### 7.1 Within one object

Two threads access the same Java object.

Example: two threads increment the same `Counter` instance.

A Java-level mechanism such as synchronization or an atomic variable may
be appropriate.

### 7.2 Within one JVM

Multiple objects and threads inside the same application process may
access shared in-memory state.

Locks, concurrent collections, and other Java concurrency mechanisms can
coordinate these threads when they use the same coordination mechanism.

### 7.3 Across multiple application instances

Imagine the Turf backend runs on three Spring Boot instances:

``` text
                 Load Balancer
                       |
          +------------+------------+
          |            |            |
       App 1         App 2         App 3
          |            |            |
          +------------+------------+
                       |
                    Database
```

A Java `synchronized` method in App 1 does not lock the corresponding
object in App 2 or App 3.

Each application instance has its own JVM memory.

Therefore, in-memory synchronization alone cannot guarantee correctness
across all instances.

When multiple application instances share a database, concurrency
control must be enforced at a shared boundary, commonly through database
transactions, constraints, conditional updates, or database locking.

We will cover these backend techniques in Phase 6.

## 8. Thread Safety in a Spring Boot Service

Consider a Spring service:

``` java
@Service
public class BookingCounterService {

    private int totalBookings = 0;

    public void recordBooking() {
        totalBookings++;
    }

    public int getTotalBookings() {
        return totalBookings;
    }
}
```

Spring services are commonly singleton-scoped by default.

That means one service instance is typically shared by requests handled
within the same application context.

If multiple request-handling threads call `recordBooking()`
concurrently, they may update the same `totalBookings` field.

The field is shared mutable state.

This implementation is not safe for concurrent increments.

A useful backend rule:

**Be cautious about storing request-specific or frequently modified
mutable data in singleton Spring beans.**

This does not mean singleton beans are inherently unsafe. Stateless
services are common and usually easier to make thread-safe.

For example, a service that receives request data as method parameters,
performs work using local variables, and does not mutate shared instance
fields is often easier to reason about.

## 9. Thread-Safety Checklist

When reviewing a class, ask:

1.  Is this object shared between threads?
2.  Does it contain mutable fields?
3.  Can multiple threads read or write those fields concurrently?
4.  Are there invariants that must always remain true?
5.  Are multi-step operations protected as a complete logical unit?
6.  Are visibility guarantees sufficient?
7.  Are all competing threads using the same lock or coordination
    mechanism?
8.  Does the solution still work if the application runs on multiple
    instances?
9.  Are we using a suitable concurrent collection or atomic operation?
10. Could the chosen synchronization create unnecessary contention or
    deadlocks?

This checklist is a starting point for code reviews, not a substitute
for understanding the behavior of each operation.

## 10. Common Interview Questions

### Q1. What is thread safety?

Thread safety means a class or component behaves correctly when multiple
threads access it concurrently, according to its intended contract.

### Q2. What commonly causes thread-safety problems?

Shared mutable state accessed concurrently without suitable coordination
is a common cause.

### Q3. Does using `synchronized` make an entire application thread-safe?

No. It protects only the code coordinated by the relevant lock. Other
shared state and operations may still have concurrency problems.

### Q4. Is an immutable object thread-safe?

An appropriately designed immutable object is generally safe to share
because its state cannot change after construction. Its construction and
publication must still be handled correctly, and referenced objects must
not expose mutable state.

### Q5. Are local variables thread-safe?

Local variables are generally stored in a method's stack frame and are
not shared between method invocations. However, if a local variable
refers to a shared mutable object, that referenced object can still be
accessed by multiple threads.

### Q6. Is a Spring singleton bean automatically thread-safe?

No. Singleton scope means the same bean instance is shared within the
application context. If it contains mutable instance state accessed by
concurrent requests, that state needs appropriate design and
coordination.

### Q7. Does `AtomicInteger` make a class thread-safe?

Not automatically. It makes supported operations on that integer atomic.
Other fields and multi-step invariants still need to be considered.

### Q8. Does Java synchronization work across multiple Spring Boot instances?

No. Java monitors and synchronized locks coordinate threads within the
JVM that share the same lock object. They do not coordinate separate
application processes.

### Q9. What is the simplest way to reduce concurrency risks?

Prefer stateless components and immutable data where practical. When
mutable shared state is necessary, use an appropriate concurrency
mechanism and protect the complete logical operation.

## 11. Practical Exercise

Build a `BankAccount` class:

-   `balance` starts at `1000`.
-   `withdraw(int amount)` checks whether enough money is available.
-   If enough money is available, it subtracts the amount.
-   `getBalance()` returns the current balance.

Then:

1.  Create one shared `BankAccount` object.
2.  Create two threads.
3.  Thread A attempts to withdraw 700.
4.  Thread B attempts to withdraw 500.
5.  Start both threads at nearly the same time.
6.  Wait for both threads to finish.
7.  Print the final balance and whether each withdrawal succeeded.

Your required invariant is:

``` text
The balance must never become negative, and withdrawals must not silently overwrite one another.
```

Answer these questions:

1.  Which fields are shared?
2.  Which operations mutate shared state?
3.  What is the critical section?
4.  Why must the balance check and deduction be coordinated together?
5.  Would an `AtomicInteger` alone be enough to protect the
    check-then-deduct operation?
6.  Would a Java `synchronized` method coordinate requests across three
    separate Spring Boot instances?

First identify the race condition and explain why the implementation is
unsafe. Then try to design a thread-safe version using a mechanism you
have already studied.

## 12. Knowledge Check

1.  What does thread safety mean?
    -   A component behaves correctly under concurrent access according
        to its contract.
2.  What three conditions commonly create concurrency risk?
    -   Shared data, mutable data, and concurrent access.
3.  Does thread safety mean that only one thread can execute at a time?
    -   No. Correct coordination is needed only where shared state or
        invariants require it.
4.  Does making one field atomic guarantee that the entire class is
    thread-safe?
    -   No. Other fields and multi-step operations still matter.
5.  Why are immutable objects useful?
    -   Their state cannot be modified after construction, reducing
        shared mutable state.
6.  Are singleton Spring beans automatically thread-safe?
    -   No. Concurrent requests may access the same bean instance.
7.  Does `synchronized` coordinate multiple JVMs?
    -   No. It coordinates threads sharing the same monitor within one
        JVM.
8.  What should be protected in a check-then-act operation?
    -   The complete logical operation, including the check and the
        state-changing action.

## 13. Important Things to Remember

1.  Thread safety means correct behavior under concurrent access.
2.  Shared mutable state is a common source of concurrency bugs.
3.  Correctness means preserving the component's intended rules and
    invariants.
4.  Immutability can reduce the need for synchronization.
5.  Synchronization coordinates threads that use the same lock.
6.  Atomic classes make specific supported operations atomic; they do
    not automatically protect an entire class.
7.  Concurrent collections help with concurrent collection access, but
    multi-step workflows may still need coordination.
8.  Stateless Spring services are generally easier to make thread-safe
    than services with mutable shared fields.
9.  Java synchronization does not coordinate separate application
    instances.
10. Backend concurrency must be handled at the correct scope: object,
    JVM, database, or distributed system.
