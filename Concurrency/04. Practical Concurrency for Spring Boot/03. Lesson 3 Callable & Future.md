# Practical Concurrency for Spring Boot - Phase 4, Lesson 3 : Callable and Future

<br>

<br>

## 1. What You Will Learn

In the previous lessons, you learned that Java can run tasks using threads and thread pools.

You also learned that instead of creating threads manually, you can submit tasks to an `ExecutorService`.

For example:

```java
ExecutorService executor = Executors.newFixedThreadPool(3);

executor.submit(() -> {
    System.out.println("Processing booking");
});
```

The executor takes the task and runs it using one of its worker threads.

But there is something missing from this example.

**What if the task needs to return an answer?**

Imagine your Turf Booking System needs to calculate the total booking price.

You want another thread to do the calculation and give you the result.

For this, Java provides two important concepts:

- `Callable`
- `Future`

In this lesson, we will learn them slowly, starting with the problem they solve.

By the end, you should understand:

- Why `Runnable` is not enough for every task.
- What `Callable` is.
- How `Callable` returns a result.
- What `Future` represents.
- How to submit a `Callable` to an executor.
- How to retrieve the result.
- Why `Future.get()` blocks.
- How to check whether a task has finished.
- How to wait with a timeout.
- How task exceptions are reported.
- How cancellation works.
- How these concepts relate to your Spring Boot Turf project.

<br>

## 2. First, Remember What Runnable Does

Before learning `Callable`, let's quickly review `Runnable`.

A `Runnable` represents a task that performs some work.

Example:

```java
Runnable task = () -> {
    System.out.println("Sending booking confirmation");
};
```

This task prints a message.

You can submit it to an executor:

```java
ExecutorService executor = Executors.newFixedThreadPool(2);

executor.submit(task);

executor.shutdown();
```

The executor runs the task on one of its worker threads.

<br>

### 2.1 The limitation of Runnable

Look at this method:

```java
public int calculatePrice() {
    return 2000;
}
```

It calculates a price and returns `2000`.

Now imagine you want to run this calculation as a task on another thread.

You might first think of using `Runnable`:

```java
Runnable task = () -> {
    int price = 2000;
};
```

But where does the value of `price` go?

The task calculates the value, but `Runnable` has no return value.

Its method is:

```java
public void run();
```

Notice the `void`.

`void` means the method does not return a value.

So, if you need a task to return a result, `Runnable` is not the right fit.

This is the problem that `Callable` solves.

<br>

## 3. What Is Callable?

`Callable` is an interface from Java's `java.util.concurrent` package.

It represents a task that can:

1. Perform some work.
2. Return a result.
3. Throw an exception if something goes wrong.

Its main method looks like this:

```java
V call() throws Exception;
```

Don't worry about the syntax yet. Let's understand each part.

<br>

### 3.1 What does V mean?

`V` represents the type of value the task will return.

For example:

```java
Callable<Integer> task = () -> {
    return 2000;
};
```

Here:

- `Callable` means we are creating a task that can return a result.
- `Integer` means the result will be an integer.
- `return 2000` is the value returned by the task.

Another example:

```java
Callable<String> task = () -> {
    return "Booking confirmed";
};
```

This task returns a `String`.

Another example:

```java
Callable<Double> task = () -> {
    return 99.50;
};
```

This task returns a `Double`.

The type inside `Callable<...>` should match the type of the value returned by the task.

<br>

### 3.2 A simple Callable example

```java
Callable<Integer> task = () -> {
    int hourlyRate = 1000;
    int hours = 2;

    return hourlyRate * hours;
};
```

The task calculates:

```text
1000 * 2 = 2000
```

It returns `2000`.

But notice something important:

**We have only created the task. We have not executed it yet.**

Just like creating a `Runnable` does not automatically execute it, creating a `Callable` does not automatically execute it.

We need an executor to run it.

<br>

## 4. Runnable vs Callable

Let's compare them directly.

| Feature | Runnable | Callable |
|---|---|---|
| Main method | `run()` | `call()` |
| Returns a result? | No | Yes |
| Can declare checked exceptions? | No, not in `run()` | Yes |
| Can be submitted to ExecutorService? | Yes | Yes |
| Common use | Work where no result is needed | Work where a result is needed |

<br>

### Example: Runnable

```java
Runnable task = () -> {
    System.out.println("Sending email");
};
```

It performs work but does not return a result.

<br>

### Example: Callable

```java
Callable<String> task = () -> {
    return "Email sent";
};
```

It performs work and returns a result.

<br>

### When should you use each one?

Use `Runnable` when you only need the task to do something.

Examples:

- Print a message.
- Send a notification when no return value is needed.
- Write a log.
- Perform a background action whose result is not required by the caller.

Use `Callable` when you need the task to return something.

Examples:

- Calculate a price.
- Generate a report and return its location.
- Retrieve a value from another service.
- Calculate a booking summary.

**Important:** You do not need to use `Callable` just because a task runs in another thread. Use it when you need a result from that task.

<br>

## 5. How Do We Execute a Callable?

We already know how to execute a `Runnable` using an `ExecutorService`.

We use the same `submit()` method for a `Callable`.

Let's see the complete example.

```java
ExecutorService executor = Executors.newFixedThreadPool(2);

Callable<Integer> task = () -> {
    int hourlyRate = 1000;
    int hours = 2;

    return hourlyRate * hours;
};

Future<Integer> future = executor.submit(task);

executor.shutdown();
```

There is a new thing here:

```java
Future<Integer> future = executor.submit(task);
```

Why doesn't `submit()` directly return `2000`?

Because the task may not have finished when `submit()` returns.

The executor accepts the task and schedules it to run on a worker thread.

The task may finish immediately, or it may take several seconds.

The calling thread needs a way to refer to the result while the task is running.

That is why `submit()` returns a `Future`.

Let's understand it.

<br>

## 6. What Is Future?

`Future<V>` is an interface from `java.util.concurrent`.

It represents the result of a task that may finish in the future.

When you submit a `Callable`, the executor gives you a `Future` representing the result that the task will produce.

Example:

```java
Callable<Integer> task = () -> {
    return 2000;
};

Future<Integer> future = executor.submit(task);
```

Here, `future` represents the result of the task.

The result type is `Integer`, so we have:

```java
Future<Integer>
```

You can think of it as a handle that lets you interact with the task's result.

It does not mean the result is already available.

The task might still be running.

<br>

### 6.1 The relationship between Callable and Future

Remember these three steps:

1. `Callable` describes the work and the result it can return.
2. `submit()` sends the task to the executor.
3. `Future` gives you access to the result when it becomes available.

The flow looks like this:

```text
Your code
   |
   | submit(callableTask)
   v
ExecutorService
   |
   | runs task on a worker thread
   v
Callable task
   |
   | returns a result
   v
Future
   |
   | get()
   v
Your code receives the result
```

This is the central idea of this lesson.

<br>

## 7. Future.get() — How to Receive the Result

The most important method of `Future` is:

```java
future.get();
```

It retrieves the result of the task.

Let's use a complete example:

```java
ExecutorService executor = Executors.newFixedThreadPool(2);

Callable<Integer> task = () -> {
    int hourlyRate = 1000;
    int hours = 2;

    return hourlyRate * hours;
};

Future<Integer> future = executor.submit(task);

Integer price = future.get();

System.out.println(price);

executor.shutdown();
```

Output:

```text
2000
```

Let's understand what happens.

<br>

### 7.1 Step-by-step execution

**Step 1: Create the executor**

```java
ExecutorService executor = Executors.newFixedThreadPool(2);
```

We create a thread pool with two worker threads.

**Step 2: Create the Callable**

```java
Callable<Integer> task = () -> {
    return 2000;
};
```

We describe a task that returns `2000`.

The task has not been submitted yet.

**Step 3: Submit the task**

```java
Future<Integer> future = executor.submit(task);
```

The executor accepts the task and schedules it for execution.

It returns a `Future<Integer>`.

**Step 4: Retrieve the result**

```java
Integer price = future.get();
```

This asks for the task's result.

If the task has already finished, `get()` returns the result immediately.

If the task is still running, the current thread waits until the task finishes.

**Step 5: Print the result**

```java
System.out.println(price);
```

The result is printed.

<br>

### 7.2 Important: get() is a blocking method

This is one of the most important things to understand about `Future`.

Suppose the task takes five seconds:

```java
Callable<String> task = () -> {
    Thread.sleep(5000);
    return "Calculation completed";
};
```

Now execute it:

```java
Future<String> future = executor.submit(task);

System.out.println("Task submitted");

String result = future.get();

System.out.println(result);
```

Possible output:

```text
Task submitted
Calculation completed
```

The second message appears only after the task finishes.

Why?

Because `future.get()` waits for the result.

While waiting, the thread that called `get()` is blocked.

<br>

### 7.3 Which thread is blocked?

This is important.

There are at least two threads involved:

- The thread that submits the task and calls `get()`.
- The executor's worker thread that runs the Callable.

The worker thread runs the task.

The calling thread waits at `get()`.

For example, if your main thread submits the task and calls `get()`, the main thread waits.

If an HTTP request thread calls `get()`, that HTTP request thread waits.

The worker thread is not the one waiting for its own result. It is executing the task.

<br>

### 7.4 Does using Future make everything non-blocking?

No.

The task can run asynchronously because the executor runs it on a worker thread.

But when you call:

```java
future.get();
```

the calling thread waits.

So this code:

```java
Future<String> future = executor.submit(task);
String result = future.get();
```

uses another thread for the task, but the current thread still waits for the result.

This is not necessarily bad. Sometimes you need the result before you can continue.

Just understand what `get()` does.

<br>

## 8. Future.isDone() — Check Whether the Task Has Finished

Sometimes you don't want to wait for the result immediately.

You may only want to check whether the task has completed.

For that, Future provides:

```java
future.isDone();
```

It returns a boolean:

- `true` means the task has completed, failed, or been cancelled.
- `false` means the task has not completed yet.

Example:

```java
ExecutorService executor = Executors.newFixedThreadPool(2);

Callable<String> task = () -> {
    Thread.sleep(3000);
    return "Done";
};

Future<String> future = executor.submit(task);

System.out.println(future.isDone());

Thread.sleep(4000);

System.out.println(future.isDone());

executor.shutdown();
```

Possible output:

```text
false
true
```

Why?

1. The task starts and sleeps for three seconds.
2. We check `isDone()` immediately. It is likely still running, so the result is `false`.
3. The main thread sleeps for four seconds.
4. We check again. The task should have finished, so the result is `true`.

`isDone()` does not wait for the task.

It only checks its completion state.

<br>

### Important difference

```java
future.isDone();
```

Checks whether the task has finished.

```java
future.get();
```

Waits for the task to finish if necessary, then retrieves its result.

<br>

## 9. Future.get(timeout, unit) — Wait Only for a Limited Time

What if a task takes too long?

Suppose your application is waiting for a result from another service.

You don't want to wait forever.

You can use:

```java
future.get(2, TimeUnit.SECONDS);
```

This means:

**Wait for the result for at most two seconds.**

Example:

```java
ExecutorService executor = Executors.newFixedThreadPool(2);

Callable<String> task = () -> {
    Thread.sleep(5000);
    return "Availability calculated";
};

Future<String> future = executor.submit(task);

try {
    String result = future.get(2, TimeUnit.SECONDS);
    System.out.println(result);
} catch (TimeoutException e) {
    System.out.println("The task took too long");
} catch (ExecutionException e) {
    System.out.println("The task failed");
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    executor.shutdown();
}
```

The task sleeps for five seconds.

But `get()` waits for only two seconds.

After two seconds, it throws `TimeoutException`.

<br>

### 9.1 Does a timeout stop the task?

No. This is very important.

A timeout means the calling thread stops waiting for the result.

It does not automatically stop the worker thread.

The task may continue running in the background.

For example:

```java
future.get(2, TimeUnit.SECONDS);
```

If the task takes five seconds:

- The caller waits for two seconds.
- The caller receives `TimeoutException`.
- The task may continue running for the remaining three seconds.

If you also want to request cancellation, you can call:

```java
future.cancel(true);
```

We will discuss cancellation later.

<br>

## 10. What Happens If the Callable Throws an Exception?

So far, our tasks have completed successfully.

But tasks can fail.

For example:

```java
Callable<Integer> task = () -> {
    int total = 1000;
    int players = 0;

    return total / players;
};
```

This code tries to divide by zero.

It throws an `ArithmeticException`.

But remember: the task is running on an executor's worker thread.

The exception happens in that worker thread.

When you submit a task using `submit()`, the executor stores the task's result or failure so that it can be reported through the returned `Future`.

When you call `get()`, a task failure is reported using `ExecutionException`.

Example:

```java
ExecutorService executor = Executors.newFixedThreadPool(2);

Callable<Integer> task = () -> {
    int total = 1000;
    int players = 0;

    return total / players;
};

Future<Integer> future = executor.submit(task);

try {
    Integer result = future.get();
    System.out.println(result);
} catch (ExecutionException e) {
    System.out.println("Task failed");

    Throwable originalError = e.getCause();

    System.out.println(originalError);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    executor.shutdown();
}
```

<br>

### 10.1 Why ExecutionException?

The original task failed on a worker thread.

The code calling `get()` needs to be informed about that failure.

So `get()` throws `ExecutionException`.

The original exception is stored as its cause.

You can access it using:

```java
e.getCause();
```

In our example, the cause is the original `ArithmeticException`.

<br>

### 10.2 Remember these exceptions

| Exception | Meaning |
|---|---|
| `ExecutionException` | The task itself failed |
| `InterruptedException` | The thread waiting for the result was interrupted |
| `TimeoutException` | The timed wait expired before a result was available |
| `CancellationException` | The task was cancelled and its result cannot be retrieved |

You do not need to memorize every detail immediately.

For now, remember:

- `ExecutionException` means the task failed.
- `InterruptedException` means the waiting thread was interrupted.
- `TimeoutException` means you waited as long as allowed.
- `CancellationException` means the task was cancelled.

<br>

## 11. InterruptedException — What Should You Do?

You will see `InterruptedException` when using methods such as:

```java
Thread.sleep(1000);
future.get();
```

It means another part of the program has requested that the current thread stop waiting or respond to interruption.

For example, a thread waiting in `future.get()` can be interrupted.

When you catch `InterruptedException`, Java clears the thread's interrupt status.

That is why this is a common and important pattern:

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

This restores the interrupt status.

For now, remember this practical rule:

**Do not silently ignore InterruptedException.**

Bad:

```java
catch (InterruptedException e) {
    // Do nothing
}
```

Better:

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

In real application code, you may also need to stop the current operation or propagate the interruption, depending on the method's responsibility.

<br>

## 12. Future.cancel() — Requesting Cancellation

What if you submit a task but later decide you no longer need it?

For example:

- A user cancels a report request.
- A calculation is no longer needed.
- A request has timed out and the work should be stopped if possible.

You can attempt to cancel a task using:

```java
future.cancel(true);
```

The method returns a boolean indicating whether cancellation succeeded.

<br>

### 12.1 What does the boolean mean?

There are two common forms:

```java
future.cancel(false);
```

This attempts to cancel the task without interrupting it if it is already running.

```java
future.cancel(true);
```

This attempts to cancel the task and requests interruption if it is already running.

For a running task, `true` allows the executor to interrupt its worker thread.

But remember:

**Interruption is a request. It is not a command that forcibly kills a thread.**

The task needs to respond to interruption.

<br>

### 12.2 A task that responds to interruption

```java
ExecutorService executor = Executors.newFixedThreadPool(2);

Callable<String> task = () -> {
    for (int i = 1; i <= 10; i++) {
        if (Thread.currentThread().isInterrupted()) {
            System.out.println("Task noticed interruption");
            return "Stopped";
        }

        System.out.println("Processing step " + i);

        Thread.sleep(1000);
    }

    return "Completed";
};

Future<String> future = executor.submit(task);

Thread.sleep(2500);

boolean cancelled = future.cancel(true);

System.out.println("Cancellation accepted: " + cancelled);

executor.shutdown();
```

What happens?

1. The task starts.
2. It prints a processing message every second.
3. The main thread waits for about 2.5 seconds.
4. The main thread requests cancellation using `cancel(true)`.
5. The worker thread is interrupted.
6. The task should respond to the interruption and stop.

There is an important detail here.

`Thread.sleep()` throws `InterruptedException` when the sleeping thread is interrupted.

In this example, we have not caught that exception inside the Callable, so it exits by throwing the exception. The Future records the task as cancelled after successful cancellation.

A more explicit version can handle interruption itself:

```java
Callable<String> task = () -> {
    try {
        for (int i = 1; i <= 10; i++) {
            System.out.println("Processing step " + i);
            Thread.sleep(1000);
        }

        return "Completed";

    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        return "Stopped because of interruption";
    }
};
```

The task catches the interruption and restores the interrupt status.

In real code, it should then exit its work rather than continue as if nothing happened.

<br>

### 12.3 What happens after cancellation?

After a successful cancellation:

```java
future.isCancelled(); // true
future.isDone();      // true
```

Calling:

```java
future.get();
```

on a cancelled Future throws:

```java
CancellationException
```

You cannot retrieve a normal result from a cancelled task.

<br>

## 13. Can Runnable Also Return a Future?

Yes. This is a detail worth knowing.

When you submit a `Runnable`, `submit()` also returns a `Future<?>`.

Example:

```java
Runnable task = () -> {
    System.out.println("Sending booking confirmation");
};

Future<?> future = executor.submit(task);
```

Why does it return a Future if Runnable has no result?

Because you may still want to:

- Check whether the task finished.
- Wait for it to finish.
- Attempt to cancel it.
- Know whether it failed.

If the Runnable completes normally, its Future's result is `null`.

Example:

```java
future.get();
```

This waits for the Runnable to finish and returns `null` if it completed successfully.

So:

- `submit(Callable)` gives you a Future containing the Callable's result.
- `submit(Runnable)` gives you a Future whose normal result is `null`.

<br>

## 14. A Complete Small Example — Put Everything Together

Let's put the most important parts together in one example.

We will calculate a booking price.

```java
import java.util.concurrent.*;

public class Main {

    public static void main(String[] args) {

        ExecutorService executor =
                Executors.newFixedThreadPool(2);

        Callable<Integer> task = () -> {
            System.out.println(
                "Calculating price on: "
                + Thread.currentThread().getName()
            );

            Thread.sleep(2000);

            int hourlyRate = 1500;
            int hours = 2;

            return hourlyRate * hours;
        };

        Future<Integer> future = executor.submit(task);

        System.out.println("Task submitted");

        try {
            Integer price = future.get();

            System.out.println("Booking price: " + price);

        } catch (ExecutionException e) {
            System.out.println(
                "Calculation failed: " + e.getCause()
            );

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();

        } finally {
            executor.shutdown();
        }
    }
}
```

Possible output:

```text
Task submitted
Calculating price on: pool-1-thread-1
Booking price: 3000
```

The exact order of the first two messages can vary because the main thread and worker thread run independently.

<br>

### Let's understand the important lines

```java
ExecutorService executor =
        Executors.newFixedThreadPool(2);
```

Creates a pool with two worker threads.

```java
Callable<Integer> task = () -> {
    Thread.sleep(2000);
    return 3000;
};
```

Creates a task that waits for two seconds and returns `3000`.

```java
Future<Integer> future = executor.submit(task);
```

Submits the task and gives us a Future representing its result.

```java
Integer price = future.get();
```

Waits for the result and retrieves it.

```java
executor.shutdown();
```

Stops the executor from accepting new tasks. Previously submitted tasks are allowed to finish.

This example demonstrates the basic Callable and Future workflow.

## 15. Using Callable and Future in a Spring Boot Application

Now let's connect this to your Turf project.

Suppose your application needs to calculate a booking price.

For learning purposes, imagine the calculation is expensive enough to run separately.

<br>

### 15.1 Configure a shared executor

In Spring Boot, don't create a new thread pool every time a service method is called.

Create a shared executor as a Spring bean.

Example using `ThreadPoolTaskExecutor`:

```java
@Configuration
public class AsyncConfig {

    @Bean
    public ThreadPoolTaskExecutor bookingTaskExecutor() {

        ThreadPoolTaskExecutor executor =
                new ThreadPoolTaskExecutor();

        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(10);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("booking-");

        return executor;
    }
}
```

Spring manages this executor as part of the application context.

The executor is shared by the components that use this bean.

<br>

### 15.2 Inject the executor into a service

```java
@Service
public class BookingPriceService {

    private final ThreadPoolTaskExecutor executor;

    public BookingPriceService(
            ThreadPoolTaskExecutor executor
    ) {
        this.executor = executor;
    }

    public Future<BigDecimal> calculatePrice(
            BigDecimal hourlyRate,
            int hours
    ) {

        Callable<BigDecimal> task = () -> {
            if (hours <= 0) {
                throw new IllegalArgumentException(
                    "Hours must be greater than zero"
                );
            }

            return hourlyRate.multiply(
                BigDecimal.valueOf(hours)
            );
        };

        return executor.submit(task);
    }
}
```

The service submits the task and returns a Future.

The caller can later retrieve the result:

```java
Future<BigDecimal> future =
        bookingPriceService.calculatePrice(
            new BigDecimal("1500"),
            2
        );

BigDecimal price = future.get();
```

This is a simplified teaching example.

A simple multiplication does not need a separate thread in a real application. The example is only showing how Callable and Future work with a Spring-managed executor.

<br>

### 15.3 Important: Future.get() inside a controller

Consider:

```java
@GetMapping("/price")
public BigDecimal getPrice() throws Exception {

    Future<BigDecimal> future =
            bookingPriceService.calculatePrice(
                new BigDecimal("1500"),
                2
            );

    return future.get();
}
```

This controller submits the calculation to a worker thread.

But then the HTTP request thread calls `get()` and waits for the result.

So the request thread is still occupied.

For a small calculation, it would be simpler to calculate the value directly.

For asynchronous HTTP responses, Spring supports other approaches, such as `CompletableFuture` and Spring MVC asynchronous request handling. We will learn `CompletableFuture` in a later lesson.

For now, understand the behavior of `Future.get()`.

## 16. What Callable and Future Do Not Solve in Your Turf Project

This section is important because concurrency concepts can easily be misunderstood.

<br>

### 16.1 They do not prevent double booking

Imagine two users try to book the same turf at the same time.

You submit both booking operations to an executor.

Does that guarantee that only one user gets the slot?

No.

A thread pool only controls how tasks run inside one application process.

It does not guarantee that two tasks cannot make conflicting booking decisions.

Your booking system still needs database-level protection, such as:

- Transactions.
- Unique constraints where appropriate.
- Row-level locking where appropriate.
- Correct booking state transitions.

The database must protect the booking data.

<br>

### 16.2 Future is not a message queue

A Future exists in memory inside the running Java application.

It is not a durable job record.

If your application crashes or restarts, the Future does not automatically resume.

For important background work, such as payment reconciliation or reliable booking notifications, you may need durable infrastructure.

For example:

- A transactional outbox.
- A persistent message broker.
- A worker that retries pending jobs.

We will discuss background-job reliability separately when it becomes relevant to the Turf system.

<br>

### 16.3 A worker thread does not automatically share the caller's transaction

Suppose a service method starts a database transaction and then submits a task to an executor.

The worker thread does not automatically inherit the original Spring transaction.

Spring's normal transaction context is thread-bound.

If the worker needs database access, it should use its own appropriate transaction boundary.

Also, if a notification must only be sent after a booking has committed, do not submit it in a way that can send the notification before the transaction commits.

<br>

## 17. Common Mistakes

<br>

### Mistake 1: Expecting Runnable to return a value

Incorrect expectation:

```java
Runnable task = () -> {
    return 2000;
};
```

`Runnable.run()` returns `void`.

Use Callable when you need a result:

```java
Callable<Integer> task = () -> {
    return 2000;
};
```

<br>

### Mistake 2: Thinking submit() returns the result

```java
Future<Integer> future = executor.submit(task);
```

This returns a Future, not the final integer.

Use:

```java
Integer result = future.get();
```

to retrieve the result.

<br>

### Mistake 3: Forgetting that get() blocks

```java
Integer result = future.get();
```

The current thread waits if the task is not finished.

Do not call it without understanding that behavior.

<br>

### Mistake 4: Thinking isDone() means the task succeeded

`isDone()` only tells you that the task has reached a completed state.

It may have succeeded, failed, or been cancelled.

<br>

### Mistake 5: Thinking a timeout stops the task

```java
future.get(2, TimeUnit.SECONDS);
```

This limits the caller's waiting time.

The task may continue running.

<br>

### Mistake 6: Ignoring ExecutionException

A submitted Callable can fail.

When you call `get()`, the failure is reported through `ExecutionException`.

Inspect its cause:

```java
e.getCause();
```

<br>

### Mistake 7: Ignoring InterruptedException

Do not silently swallow interruption.

A common response is:

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

<br>

### Mistake 8: Thinking cancel(true) forcibly kills a thread

It requests interruption.

The task needs to cooperate and stop.

<br>

### Mistake 9: Creating a new executor for every task

This can create too many threads and waste resources.

Use a shared, configured executor in a Spring Boot application.

<br>

### Mistake 10: Using another thread for work that takes almost no time

Creating and coordinating tasks has a cost.

If a calculation is just:

```java
int total = 1500 * 2;
```

there is no reason to create a separate thread for it.

Use concurrency when it provides a real benefit.

<br>

## 18. Interview Questions and Answers

<br>

### Q1. What is Callable?

`Callable<V>` is an interface that represents a task which can return a result of type `V` and throw an exception.

<br>

### Q2. What is the difference between Runnable and Callable?

`Runnable` has a `void run()` method and does not return a result.

`Callable` has a `call()` method that returns a value.

<br>

### Q3. What is Future?

`Future<V>` represents the result of an asynchronous computation. It allows you to retrieve the result, check completion, and attempt cancellation.

<br>

### Q4. Does submit() wait for the Callable to finish?

No. `submit()` submits the task and returns a Future. The task may still be running.

<br>

### Q5. What does Future.get() do?

It retrieves the task's result. If the task is still running, the calling thread waits until the result is available.

<br>

### Q6. Is Future.get() blocking?

Yes. The calling thread blocks if the result is not ready.

<br>

### Q7. What is the difference between get() and get(timeout, unit)?

`get()` waits until the task completes.

The timed version waits only for the specified duration. If the result is not ready in time, it throws `TimeoutException`.

<br>

### Q8. Does TimeoutException cancel the task?

No. It means the caller stopped waiting after the timeout. The task may continue running.

<br>

### Q9. What is ExecutionException?

It is thrown by `Future.get()` when the submitted task fails. The original exception can be accessed using `getCause()`.

<br>

### Q10. What does cancel(true) do?

It attempts to cancel the task and requests interruption if the task is running. The task must respond to interruption.

<br>

### Q11. Does isDone() mean the task succeeded?

No. It means the task reached a completed state. It may have succeeded, failed, or been cancelled.

<br>

### Q12. Can submit(Runnable) return a Future?

Yes. It returns a `Future<?>`. If the Runnable completes normally, its result is `null`.

<br>

### Q13. Does Future make an HTTP request non-blocking?

Not automatically. If the controller calls `get()`, the request thread blocks while waiting.

<br>

### Q14. Can Future prevent two users from booking the same turf slot?

No. Future is not a database concurrency-control mechanism. Booking correctness must be protected through database transactions and constraints or locking.

<br>

**Question:** Which method checks whether the task has finished without waiting?

**Answer:**

```java
future.isDone();
```

It returns `true` or `false`.

<br>

**Question:** How do you wait for a result for at most three seconds?

**Answer:**


### Practice 6: Understand a task failure

**Question:** A Callable throws `IllegalStateException`. What does `Future.get()` throw?

**Answer:**

It throws `ExecutionException`.

```java
e.getCause();
```

<br>

### Practice 7: Request cancellation

**Question:** How do you request cancellation and interruption of a running task?

**Answer:**

```java
future.cancel(true);
```

This requests interruption. It does not forcibly kill the worker thread.

<br>

### Practice 8: Explain the output order

Consider:

```java
Future<String> future = executor.submit(() -> {
    Thread.sleep(2000);
    return "Done";
});

System.out.println("Submitted");

String result = future.get();

System.out.println(result);
```

**Question:** Why does `Done` print after the task finishes?

**Answer:**

- The task is submitted to the executor.
- The main thread prints `Submitted`.
- The task runs on a worker thread.
- The main thread reaches `future.get()` and waits.
- When the task finishes, `get()` returns `"Done"`.
- The main thread prints `Done`.

The main thread waits because `get()` is blocking.

<br>

**Answer:**

`Runnable` is enough because you only need the task to perform work.

<br>

### Practice 10: Choose Runnable or Callable

**Question:** You need to calculate a booking price on a worker thread and retrieve the calculated amount. Which should you use?

**Answer:**

`Callable<BigDecimal>` (or another suitable numeric type), because you need the task to return a result.

## 20. System Design Questions for Your Turf Project

<br>

### Question 1: Should every booking price calculation use Callable?

**Answer:**

No.

If the calculation is simple, such as multiplying an hourly rate by the number of hours, normal synchronous code is better.

Use another thread only when the work is substantial or can usefully happen concurrently with other work.

<br>

### Question 2: Two users try to book the same slot. Can an executor decide who gets it?

**Answer:**

No.

An executor decides which worker runs a task. It does not enforce booking rules.

The database must protect the booking operation using appropriate transactions, constraints, and locking.

<br>

### Question 3: A notification task is submitted, then the application crashes. Will its Future resume after restart?

**Answer:**

No.

The Future and task state are in memory. They are lost when the application process stops.

For reliable notifications, use durable job processing, such as a transactional outbox and a worker that can retry pending records.

<br>

### Question 4: A task is taking too long. Is get(timeout, unit) enough to stop it?

**Answer:**

No.

It limits how long the calling thread waits. If the task should also stop, request cancellation and make sure the task responds to interruption.

<br>

### Question 5: Does a worker thread automatically use the controller's database transaction?

**Answer:**

No.

Spring's normal transaction context is thread-bound. A task running on another thread does not automatically share the original transaction.

The worker should have its own appropriate transaction boundary if it needs database access.

<br>

## 21. Key Takeaways

Let's finish with the most important ideas.

1. `Runnable` represents work that does not return a result.
2. `Callable<V>` represents work that can return a result of type `V`.
3. You submit a Callable using `ExecutorService.submit()`.
4. `submit()` returns a `Future<V>`.
5. A Future represents the result that the task will produce.
6. `Future.get()` retrieves the result.
7. If the task is still running, `get()` blocks the calling thread.
8. `isDone()` checks whether the task has completed.
9. Timed `get()` limits how long the caller waits.
10. A timeout does not automatically cancel the task.
11. Task failures are reported through `ExecutionException`.
12. Cancellation requests interruption; it does not forcibly kill a thread.
13. A Future is in-memory state, not a durable background-job system.
14. Neither Callable nor Future prevents two users from booking the same slot.

**The most important thing to remember:**

- `Callable` is the task that can return an answer.
- `Future` is how you access that answer later.
