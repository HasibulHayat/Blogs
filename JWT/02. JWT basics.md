# What Happens If Someone Changes Data Inside a JWT?

<br>
<br>

## 1. Imagine the Original JWT

Suppose Rahim logs into your application.

Your Spring Boot application generates a JWT with this payload:

```json
{
  "sub": "rahim",
  "role": "USER"
}
```

The backend signs this payload using its secret key.

Remember, a JWT has three parts:

```text
HEADER.PAYLOAD.SIGNATURE
```

The signature is calculated using the original header, payload, and signing key.

<br>

## 2. What If Someone Changes the Payload?

Imagine Rahim wants to become an administrator.

He decodes the JWT and changes the payload from:

**Original payload:**

```json
{
  "sub": "rahim",
  "role": "USER"
}
```

**Modified payload:**

```json
{
  "sub": "rahim",
  "role": "ADMIN"
}
```

Can he do this?

**Yes!** Anyone who has a normal signed JWT can decode and modify its header or payload.

But there is a problem for the attacker: the original signature was created using the original payload.

Changing the payload does not automatically generate a new valid signature.

<br>

## 3. Why Does the Server Reject the Modified JWT?

Let's understand how signing and verification work.

When your backend originally creates the token:

```text
Original Header + Original Payload + Secret Key
                    |
                    v
              Generate Signature
                    |
                    v
               Original JWT
```

Now someone changes the payload:

```text
Modified Payload + Original Signature
                    |
                    v
             Send to Backend
                    |
                    v
          Verify the JWT Signature
                    |
                    v
             Signature Invalid!
                    |
                    v
              Reject the Token
```

The backend calculates and checks the expected signature using its signing key.

Because the payload has changed, the signature no longer matches.

The backend therefore rejects the token.

Typically, the API returns:

```http
HTTP/1.1 401 Unauthorized
```
<br>

## 4. How Does This Work in Spring Boot?

Remember our `JwtService.java` class?

We used this method:

```java
private Claims extractAllClaims(String token) {
    return Jwts.parser()
            .verifyWith(signingKey)
            .requireIssuer("my-spring-app")
            .requireAudience("my-spring-api")
            .build()
            .parseSignedClaims(token)
            .getPayload();
}
```

Let's understand the important lines.

**`verifyWith(signingKey)`**

This tells JJWT which secret key to use when verifying the token's signature.

**`parseSignedClaims(token)`**

This parses the signed JWT and verifies its signature before returning the claims.

If someone modifies the payload, JJWT throws an exception instead of returning trusted claims.

Our `JwtAuthenticationFilter` catches JWT exceptions and does not authenticate the request.

Therefore, the attacker cannot simply change `USER` to `ADMIN` and access administrator endpoints.

<br>

## 5. What If Someone Changes Both the Payload AND Signature?

Good question!

An attacker can modify both the payload and signature.

However, generating a valid replacement signature requires the signing key.

For example:

1. The attacker changes `USER` to `ADMIN`.
2. The attacker tries to generate a new signature.
3. The attacker does not know your signing secret.
4. The attacker cannot generate a valid signature.

Assuming your application uses a secure signing algorithm and properly protects its key, the modified token will be rejected.

**Important:** If your JWT signing secret is stolen, an attacker may be able to create completely valid JWTs, including tokens with administrator privileges.

That is why you must:
- Use a strong, randomly generated secret.
- Never expose the secret to the frontend.
- Never commit the secret to GitHub.
- Store it in environment variables or a secrets manager.
- Protect access to your production environment.

<br>

## 6. What Can Someone Do With a JWT?

| Action | Possible? |
|---|---|
| Read the JWT payload | Yes |
| Decode the JWT payload | Yes |
| Modify the JWT payload | Yes |
| Change the payload and keep the original signature valid | No |
| Generate a valid modified signature without the signing key | No, assuming secure cryptography |
| Create valid tokens if the signing key is stolen | Yes |

<br>

## 7. Important: Signature Provides Integrity, Not Confidentiality

These two words are important.

**Integrity:** Ensures that the signed data has not been modified without detection.

**Confidentiality:** Ensures that unauthorized people cannot read the data.

A normal signed JWT provides integrity, but not confidentiality.

Anyone who obtains the token can generally decode and read its payload.

Never store passwords, secret keys, or sensitive information inside a normal JWT payload.

<br>

## 8. The Most Important Thing to Remember

Think of a JWT as a document with a tamper-evident seal.

- The payload contains information.
- The signature acts like a security seal.
- Anyone can read the document.
- Anyone can try to modify the document.
- But modifying the document breaks the original seal.
- The backend checks the seal before trusting the document.

**The main lesson:**

A JWT is not protected because nobody can edit it.

It is protected because the backend can detect when someone has edited it.

<br>

That is the purpose of the JWT signature!
